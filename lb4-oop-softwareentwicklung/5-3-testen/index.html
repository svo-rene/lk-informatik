5.3 Testen

Einführung 2Übungen 3Vertiefung 2

Ein Getränkeautomat nimmt jede Münze an, nur nicht das 2-Euro-Stück mit einem bestimmten Prägejahr. Ein Online-Shop gewährt „ab 50 € versandkostenfrei“, berechnet aber bei genau 50,00 € trotzdem Versand. Solche Fehler fallen beim Ausprobieren selten auf, denn wer probiert schon genau diese Werte? Testen heißt: gezielt die Eingaben auswählen, bei denen Fehler am wahrscheinlichsten sind, und das Ergebnis automatisch prüfen lassen – nicht einmal, sondern nach jeder Änderung.

Testfälle mit Eingabe, erwarteter und tatsächlicher Ausgabe kennst du aus vielen Aufgaben dieses Kurses. Auf dieser Seite lernst du, wie man Testfälle systematisch auswählt und sie als Testdatei neben das Modul legt, sodass jede Person im Team sie mit einem Klick laufen lassen kann. Im V-Modell (Seite 5.2) sind das Modultests.

Schritt 1: Welche Werte soll ich testen? Äquivalenzklassen und Grenzwerte

Alle Eingaben auszuprobieren, ist unmöglich – man muss geschickt auswählen. Im Video siehst du an der Funktion ist_unterpunktet (weniger als 5 Punkte), wie man die Eingaben auf einem Zahlenstrahl in Klassen einteilt und an welchen Stellen man testet. Achte darauf, warum die Vertreter 2 und 10 einen Fehler im Code nicht finden, der Grenzwert 5 aber schon – und woher das erwartete Ergebnis kommt.

Zum Nachlesen: Testfall und Spezifikation

Ein Testfall besteht aus einer Eingabe, dem erwarteten Ergebnis und dem tatsächlichen Ergebnis. Das erwartete Ergebnis stammt immer aus der Spezifikation (Aufgabenstellung, User Story, Akzeptanzkriterium) – nie aus dem Code. Wer das Erwartete aus dem Code abliest, prüft nur, ob der Code das tut, was er tut.

Alle möglichen Eingaben zu testen, ist fast nie möglich. Schon eine Funktion mit einem int-Parameter hat unendlich viele Eingaben. Deshalb wählt man geschickt aus.

Äquivalenzklassen

Eingaben, die laut Spezifikation gleich behandelt werden, bilden eine Äquivalenzklasse. Es gibt gültige Klassen (normale Verarbeitung) und ungültige Klassen (Fehlermeldung, ValueError). Aus jeder Klasse genügt zunächst ein Vertreter, denn verhält sich das Programm für einen Wert der Klasse richtig, wird es das für die anderen vermutlich auch.

Grenzwertanalyse

Fehler stecken besonders oft an den Rändern der Klassen: < statt <=, range(1, n) statt range(1, n + 1). Deshalb testet man an jeder Grenze den Wert direkt davor und direkt dahinter (bei ganzen Zahlen also den letzten Wert der einen und den ersten Wert der nächsten Klasse).

Kurz geprüft 1: Das Extraleben AFB I

In einem Spiel gibt es ab 1000 Punkten ein Extraleben. Punkte sind ganze Zahlen ab 0; negative Werte sind ungültig (ValueError). Nenne die Äquivalenzklassen mit je einem Vertreter und alle Grenzwerte, die du testen würdest.

Lösung zeigen

Drei Klassen: ungültig unter 0 (z. B. −5 → ValueError), gültig 0 bis 999 (z. B. 400 → kein Extraleben), gültig ab 1000 (z. B. 3000 → Extraleben). Grenzwerte: −1 | 0 und 999 | 1000. Eine obere Grenze gibt es laut Spezifikation nicht.

Danach: Aufgabe 5.3.1 – Äquivalenzklassen und Grenzwerte beim Lesewettbewerb.

Weiter mit Schritt 2: Tests mit assert in einer Testdatei →

Schritt 2: Tests mit assert in einer Testdatei

Jetzt prüft Python die Testfälle selbst. Im Video lernst du assert erst in der Kommandozeile kennen, dann legt Thonny neben das Modul kurshalbjahr.py die Testdatei test_kurshalbjahr.py. Achte auf die Meldung beim ersten roten Test: Sie nennt Eingabe, Erwartung und tatsächliches Ergebnis – damit findest du den Fehler im Modul sofort. Kurz erklärt wird auch, wie for punkte, erwartet in [(0, True), …] die Paare auspackt.

Zum Nachlesen: Tests in Python mit assert

assert bedingung, meldung tut nichts, wenn die Bedingung wahr ist. Ist sie falsch, bricht Python mit AssertionError: meldung ab. Die Meldung schreibst du immer im Muster „erwartet …, tatsächlich …“, dann siehst du sofort, was schiefging:

ergebnis = ist_unterpunktet(5)
assert ergebnis == False, f"5 Punkte: erwartet False, tatsächlich {ergebnis}"
  • Testfunktionen: Zusammengehörige Prüfungen stehen in einer Funktion, deren Name mit test_ beginnt, z. B. def test_grenzen():. Jede Testfunktion baut sich ihre Objekte selbst neu auf, damit kein Test vom anderen abhängt.
  • Testdatei neben dem Modul: Zu aufzug.py gehört test_aufzug.py im selben Ordner. Sie importiert das Modul, enthält nur Tests und startet sie unter if __name__ == "__main__":. Das Modul selbst bleibt frei von Testcode.

Den vollständigen Ablauf aus dem Video – Klassen, Grenzen, Testdatei, Fehler – findest du in Beispiel 1:

Beispiel 1 einfach Unterpunktet oder nicht? – Klassen, Grenzen, Testdatei

Ausgangssituation: In der Oberstufe gilt ein Kurshalbjahr mit weniger als 5 Punkten als unterpunktet. Punkte gibt es von 0 bis 15; andere Werte sind Tippfehler. Spezifikation der Funktion ist_unterpunktet(punkte: int) -> bool: 0 bis 4 → True, 5 bis 15 → False, sonst ValueError. Jemand hat programmiert:

# kurshalbjahr.py
def ist_unterpunktet(punkte: int) -> bool:
    if punkte < 0 or punkte > 15:
        raise ValueError("Punkte müssen zwischen 0 und 15 liegen")
    return punkte <= 5
  1. Äquivalenzklassen bilden: U1 ungültig (unter 0), G1 gültig 0…4 → True, G2 gültig 5…15 → False, U2 ungültig (über 15). Warum: Innerhalb jeder Klasse verlangt die Spezifikation dasselbe Verhalten.
  2. Grenzwerte bestimmen: −1 | 0, 4 | 5, 15 | 16. Warum: Je zwei Werte an jeder der drei Grenzen, insgesamt sechs Tests statt unendlich vieler.
  3. Erwartete Werte aus der Spezifikation: −1 → ValueError, 0 → True, 4 → True, 5 → False, 15 → False, 16 → ValueError. Warum nicht aus dem Code: Der Code liefert bei 5 True – wer das abschreibt, findet den Fehler nie.
  4. Testdatei neben das Modul legen: 
    # test_kurshalbjahr.py
from kurshalbjahr import ist_unterpunktet

def wirft_value_error(funktion, *argumente) -> bool:
    try:
        funktion(*argumente)
    except ValueError:
        return True
    return False

def test_gueltige_grenzen():
    for punkte, erwartet in [(0, True), (4, True), (5, False), (15, False)]:
        ergebnis = ist_unterpunktet(punkte)
        assert ergebnis == erwartet, f"{punkte} Punkte: erwartet {erwartet}, tatsächlich {ergebnis}"

def test_ungueltige_grenzen():
    assert wirft_value_error(ist_unterpunktet, -1), "-1 Punkte: erwartet ValueError"
    assert wirft_value_error(ist_unterpunktet, 16), "16 Punkte: erwartet ValueError"

if __name__ == "__main__":
    test_gueltige_grenzen()
    test_ungueltige_grenzen()
    print("Alle Tests bestanden.")
    Warum eine Schleife über Paare: Jeder neue Grenzwert ist eine Zeile mehr in der Liste, nicht ein neuer Block Code.
  5. Test starten: test_kurshalbjahr.py in Thonny ausführen. Die letzte Zeile der Ausgabe lautet: 
    AssertionError: 5 Punkte: erwartet False, tatsächlich True
    Die Meldung zeigt den Fehler genau: Bei 5 Punkten stimmt das Ergebnis nicht. Ursache ist <= 5 statt < 5.

Ergebnis: Nach der Korrektur return punkte < 5 gibt die Testdatei „Alle Tests bestanden.“ aus.

Kontrolle: Ein Vertreter aus der Mitte (z. B. 2 oder 10) hätte den Fehler nicht gefunden – beide liefern auch mit <= 5 das Richtige.

Kurz geprüft 2: Wer hat den Fehler – Modul oder Test? AFB II

Das Modul kurshalbjahr.py ist schon korrigiert (return punkte < 5). Jemand ergänzt in der Testdatei die Zeile assert ist_unterpunktet(4) == False, "4 Punkte: erwartet False". Was gibt Python aus? Wo steckt der Fehler, und was fehlt außerdem an der Meldung?

Lösung zeigen

Python bricht ab mit AssertionError: 4 Punkte: erwartet False. Der Fehler steckt im Test: Laut Spezifikation sind 4 Punkte unterpunktet, erwartet ist also True. Der Meldung fehlt außerdem das „tatsächlich …“ – mit f"…, tatsächlich {ergebnis}" hätte man sofort gesehen, dass das Modul True liefert.

Weiter mit Schritt 3: Einen ValueError erwarten →

Schritt 3: Einen ValueError erwarten

Für −1 und 16 verlangt die Spezifikation einen ValueError. Ruft ein Test die Funktion einfach auf, bricht er aber mit genau diesem Fehler ab. Im Video siehst du die Hilfsfunktion wirft_value_error, die den Fehler mit try/except abfängt und stattdessen True oder False liefert. Kurz erklärt werden try/except und *argumente.

Zum Nachlesen: Fehler erwarten

Soll eine Eingabe einen ValueError auslösen, prüfst du das mit einer kleinen Hilfsfunktion:

def wirft_value_error(funktion, *argumente) -> bool:
    """True, wenn der Aufruf funktion(*argumente) einen ValueError auslöst."""
    try:
        funktion(*argumente)
    except ValueError:
        return True
    return False

assert wirft_value_error(ist_unterpunktet, 16), "16 Punkte: erwartet ValueError"

*argumente sammelt alle weiteren Argumente ein und reicht sie an die Funktion weiter. Du kannst auch eine Methode übergeben, z. B. wirft_value_error(Aufzug().einsteigen, 0).

Kurz geprüft 3: Was liefert die Hilfsfunktion? AFB I

Was liefern wirft_value_error(ist_unterpunktet, 0) und wirft_value_error(ist_unterpunktet, 99)? Welchen Wert hat argumente jeweils innerhalb der Hilfsfunktion?

Lösung zeigen

Bei 0 gibt es keinen Fehler (0 Punkte sind gültig), also False; argumente ist das Tupel (0,). Bei 99 löst ist_unterpunktet einen ValueError aus, except fängt ihn ab, Ergebnis True; argumente ist (99,).

Weiter mit Schritt 4: Alle Tests auf einmal →

Schritt 4: Alle Tests auf einmal – Testrunner, Zustand prüfen, Fehler finden

Der erste AssertionError beendet das Programm – die übrigen Tests laufen dann gar nicht mehr. Im Video testest du die Klasse Aufzug mit dem kleinen Testrunner von dieser Seite, der alle Tests nacheinander aufruft und am Ende zählt. Achte darauf, welche Tests rot werden, obwohl der Rückgabewert stimmt: Bei Methoden mit Nebenwirkung muss der Test auch den Zustand prüfen. Kurz erklärt wird, wie man Funktionen in eine Liste packt und mit .__name__ ihren Namen bekommt.

Zum Nachlesen: Alle Tests auf einmal

Ein AssertionError beendet das Programm beim ersten Fehler. Damit trotzdem alle Tests laufen und du eine Übersicht bekommst, nutzt du am Ende der Testdatei diesen kleinen Testrunner. Er ruft die Testfunktionen aus einer Liste nacheinander auf und fängt den AssertionError ab:

if __name__ == "__main__":
    tests = [test_normalfall, test_genau_630_kg, test_631_kg]
    fehler = 0
    for test in tests:
        try:
            test()
            print("ok     ", test.__name__)
        except AssertionError as meldung:
            print("FEHLER ", test.__name__, "–", meldung)
            fehler += 1
    print(f"{len(tests) - fehler} von {len(tests)} Tests bestanden")
Beispiel 2 komplex Der Aufzug – zwei Grenzen, ein Zustand und ein versteckter Fehler

Ausgangssituation: Für ein Simulationsprogramm des Schulaufzugs gibt es die Klasse Aufzug. Spezifikation: höchstens 8 Personen und höchstens 630 kg. einsteigen(gewicht_kg) nimmt eine Person nur auf, wenn danach beide Grenzen eingehalten sind, und gibt dann True zurück. Sonst gibt sie False zurück und nichts ändert sich. Gewichte unter 1 kg oder über 250 kg sind Tippfehler (ValueError).

# aufzug.py  (Model)
class Aufzug:
    MAX_PERSONEN = 8
    MAX_LAST_KG = 630

    def __init__(self):
        self.__personen = 0
        self.__last_kg = 0

    def personen(self) -> int:
        return self.__personen

    def last(self) -> int:
        return self.__last_kg

    def einsteigen(self, gewicht_kg: int) -> bool:
        if gewicht_kg <= 0 or gewicht_kg > 250:
            raise ValueError("unmögliches Gewicht")
        self.__personen += 1
        self.__last_kg += gewicht_kg
        if self.__personen > Aufzug.MAX_PERSONEN or self.__last_kg >= Aufzug.MAX_LAST_KG:
            return False
        return True
  1. Grenzen finden: Es gibt drei: das Gewicht einer Person (1…250), die Gesamtlast (630 erlaubt, 631 nicht) und die Personenzahl (8. Person erlaubt, 9. nicht). Warum alle drei: Jede Grenze ist eine eigene Stelle im Code, an der ein Vergleich falsch sein kann.
  2. Den Zustand mitprüfen: Bei einer abgelehnten Person genügt es nicht, False zu prüfen. Die Spezifikation sagt auch „nichts ändert sich“, also prüft der Test zusätzlich personen() bzw. last(). Warum: Methoden mit Nebenwirkung können das richtige Ergebnis zurückgeben und trotzdem den Zustand verderben.
  3. Testfälle aufstellen:
    TestAufrufeerwartet
    Normalfall70, 80, 65 kgdreimal True, 3 Personen, 215 kg
    genau 630 kg4 × 150 kg, dann 30 kgTrue
    631 kg4 × 150 kg, dann 31 kgFalse, Last bleibt 600
    9. Person8 × 50 kg, dann 50 kgFalse, Personen bleiben 8
    Gewicht0, 251, 250 kgValueError, ValueError, kein ValueError
  4. Testdatei schreiben (Hilfsfunktion wirft_value_error wie oben): 
    # test_aufzug.py
from aufzug import Aufzug

def wirft_value_error(funktion, *argumente) -> bool:
    try:
        funktion(*argumente)
    except ValueError:
        return True
    return False

def test_normalfall():
    a = Aufzug()
    for gewicht in [70, 80, 65]:
        assert a.einsteigen(gewicht) == True, f"{gewicht} kg: erwartet True"
    assert a.personen() == 3, f"Personen: erwartet 3, tatsächlich {a.personen()}"
    assert a.last() == 215, f"Last: erwartet 215, tatsächlich {a.last()}"

def test_genau_630_kg():
    a = Aufzug()
    for gewicht in [150, 150, 150, 150]:
        a.einsteigen(gewicht)
    ergebnis = a.einsteigen(30)                 # danach genau 630 kg
    assert ergebnis == True, f"bei 630 kg: erwartet True, tatsächlich {ergebnis}"

def test_631_kg():
    a = Aufzug()
    for gewicht in [150, 150, 150, 150]:
        a.einsteigen(gewicht)
    ergebnis = a.einsteigen(31)                 # danach wären es 631 kg
    assert ergebnis == False, f"bei 631 kg: erwartet False, tatsächlich {ergebnis}"
    assert a.last() == 600, f"Last: erwartet 600, tatsächlich {a.last()}"

def test_neunte_person():
    a = Aufzug()
    for i in range(8):
        a.einsteigen(50)

    assert a.personen() == 8, f"Personen: erwartet 8, tatsächlich {a.personen()}"

def test_unmoegliches_gewicht():
    assert wirft_value_error(Aufzug().einsteigen, 0), "0 kg: erwartet ValueError"
    assert wirft_value_error(Aufzug().einsteigen, 251), "251 kg: erwartet ValueError"

            raise ValueError("unmögliches Gewicht")
        if self.__personen + 1 > Aufzug.MAX_PERSONEN:
            return False

Ergebnis: Nach der Korrektur meldet der Testrunner „5 von 5 Tests bestanden“.

Kontrolle: Der Normalfall war schon mit dem fehlerhaften Code grün. Ohne Grenzwerte und Zustandsprüfung hätte niemand die Fehler bemerkt. Die Testdatei bleibt im Repository: Ändert später jemand einsteigen, zeigen dieselben fünf Tests sofort, ob noch alles stimmt.

Fehler finden mit Tests

  1. Test schreiben, der den Fehler zeigt (er muss zuerst fehlschlagen).
  2. Meldung lesen: Welche Eingabe, was erwartet, was tatsächlich?
  3. Ursache im Code suchen, meist an einem Vergleich, einer Schleifengrenze oder in der Reihenfolge „ändern, dann prüfen“.
  4. Korrigieren und alle Tests erneut laufen lassen, nicht nur den neuen. So merkst du, wenn die Korrektur an anderer Stelle etwas kaputt macht.
  5. Den Test behalten. Jeder gefundene Fehler wird ein Test, damit er nie unbemerkt zurückkommt.
Hinweis: Und was ist mit unittest und pytest?

In der Praxis nutzt man Test-Werkzeuge wie unittest (in Python eingebaut) oder pytest. Sie finden alle Funktionen test_… automatisch, zählen die Ergebnisse und zeigen bei einem Fehler Erwartung und Ergebnis an – im Prinzip das, was unser kleiner Testrunner tut. Für den Kurs reichen assert und der Runner; sie laufen in Thonny ohne Installation.

Kurz geprüft 4: Richtige Antwort, falscher Zustand AFB II

Mit der fehlerhaften Klasse Aufzug aus Beispiel 2 wird ausgeführt: a = Aufzug(), dann a.einsteigen(250), a.einsteigen(250), a.einsteigen(200). Was liefert der dritte Aufruf, und welche Werte haben danach a.last() und a.personen()? Was ergäbe sich mit der korrigierten Methode?

Lösung zeigen

Fehlerhaft: Der dritte Aufruf liefert False (700 ≥ 630) – das ist richtig. Trotzdem sind a.last() = 700 und a.personen() = 3, weil vor der Prüfung erhöht wurde. Korrigiert: ebenfalls False, aber a.last() = 500 und a.personen() = 2. Nur ein Test, der auch den Zustand prüft, sieht den Unterschied.

Praxisbezug: Testen als Beruf

Alltag: Jedes Mal, wenn eine Banking-App ein Update bekommt, laufen vorher Tausende automatischer Tests – auch für 0,00 €, für den höchsten erlaubten Betrag und für einen Cent darüber.

Beruf: Softwaretesterinnen und -tester bzw. Fachleute für Qualitätssicherung entwerfen Testfälle aus Anforderungen, oft mit genau den Verfahren dieser Seite. Für den Einstieg gibt es international anerkannte Zertifikate (z. B. ISTQB Certified Tester). In vielen Teams schreiben auch die Entwicklerinnen und Entwickler selbst Modultests; ohne grüne Tests wird kein Pull Request übernommen.

Zusammenfassung

Testfälle wählt man systematisch: Die Eingaben werden in Äquivalenzklassen eingeteilt (gültige und ungültige), aus jeder Klasse kommt ein Vertreter, und an jeder Klassengrenze werden der Wert direkt davor und direkt dahinter getestet. Das erwartete Ergebnis stammt immer aus der Spezifikation. In Python stehen die Tests in einer eigenen Datei test_<modul>.py neben dem Modul, in Funktionen test_…() mit assert bedingung, f"erwartet …, tatsächlich …". Erwartete Fehler prüft die Hilfsfunktion wirft_value_error, und ein kleiner Testrunner lässt alle Tests laufen und zählt die Fehler. Bei Methoden mit Nebenwirkung prüft ein guter Test auch den Zustand danach.

Das Wichtigste

Testfall: Besteht aus Eingabe, erwartetem Ergebnis (aus der Spezifikation) und tatsächlichem Ergebnis. Der Test ist bestanden, wenn beide Ergebnisse übereinstimmen.

Äquivalenzklasse: Menge von Eingaben, die laut Spezifikation gleich behandelt werden. Es gibt gültige und ungültige Klassen; aus jeder testet man mindestens einen Vertreter.

Grenzwertanalyse: An jeder Klassengrenze testet man den Wert direkt davor und direkt dahinter, weil dort die meisten Fehler entstehen.

Tests in Python: Sie stehen in einer eigenen Datei test_<modul>.py, in Funktionen test_…(), mit assert bedingung, "meldung". Ohne Klammern schreiben: assert (bedingung, "meldung") prüft ein Tupel und ist immer wahr.

Aufgabe 5.3.1: Äquivalenzklassen und Grenzwerte – der Lesewettbewerb AFB I–II

Beim Lesewettbewerb der Unterstufe gibt es für jedes gelesene Buch Punkte nach seiner Seitenzahl: unter 100 Seiten 1 Punkt, 100 bis 299 Seiten 2 Punkte, ab 300 Seiten 3 Punkte. Seitenzahlen unter 1 oder über 2000 sind Tippfehler (ValueError). Die Funktion heißt lesepunkte(seiten: int) -> int.

  1. Gib alle Äquivalenzklassen an, kennzeichne gültige und ungültige und nenne je einen Vertreter.
  2. Gib alle Werte an, die bei der Grenzwertanalyse getestet werden, jeweils mit erwartetem Ergebnis.
  3. Begründe, warum die Vertreter aus a) allein nicht ausreichen.
Aufgabe 5.3.2: Eine Testdatei schreiben und den Fehler finden AFB II

So hat ein Mitschüler lesepunkte aus Aufgabe 5.3.1 programmiert:

# lesepunkte.py
def lesepunkte(seiten: int) -> int:
    if seiten < 1 or seiten >= 2000:
        raise ValueError("Seitenzahl ungültig")
    if seiten <= 100:
        return 1
    elif seiten < 300:
        return 2
    return 3
  1. Speichere das Modul in Thonny und lege daneben test_lesepunkte.py an: eine Testfunktion für die Vertreter, eine für die gültigen Grenzwerte, eine für die ungültigen Grenzwerte (mit wirft_value_error) und den Testrunner. Alle Meldungen im Muster „erwartet …, tatsächlich …“.
  2. Führe die Tests aus und notiere die Ausgabe.
  3. Korrigiere das Modul, bis alle Tests bestehen. Notiere, wie viele Fehler es gab und durch welchen Test du jeden gefunden hast.

Wenn du in einer Testfunktion mehrere Grenzwerte in einer Schleife prüfst und einer davon einen ValueError auslöst, bricht der Test mit einer Fehlermeldung ab. Fange das mit try/except ValueError ab und setze dann ergebnis = "ValueError".
