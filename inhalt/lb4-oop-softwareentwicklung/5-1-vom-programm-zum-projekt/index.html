Warum Objektorientierung?

Objektorientierung hilft dir, reale Probleme als Modell aus Objekten darzustellen. Statt nur einzelne Funktionen zu schreiben, strukturierst du dein Programm.

Vier Grundprinzipien sind für die OOP wichtig:

  • Kapselung: Daten und Methoden gehören zusammen in eine Klasse; der Zugriff von außen erfolgt nur über Methoden.
  • Abstraktion: Ein Objekt zeigt nur das, was von außen wichtig ist.
  • Vererbung: Gemeinsame Eigenschaften werden in einer Basisklasse gebündelt.
  • Polymorphie: Gleiche Methoden können unterschiedlich umgesetzt werden.

Schritt 1: Ein Programm – mehrere Dateien

Kleine Programme passen in eine Datei, größere werden darin unübersichtlich. Deshalb verteilt man die Klassen auf mehrere Dateien – jede Python-Datei ist ein Modul – und verbindet sie mit import. Im Video entsteht der Fuhrpark aus Beispiel 1 in drei Dateien. Achte auf die Reiter oben im Editor und im Tafelbild auf die Pfeile „importiert“. Kurz erklärt werden die beiden Schreibweisen from fahrzeug import Fahrzeug und import fahrzeug.

Zum Nachlesen: Wenn Programme größer werden …

Kleine Programme kann man noch komplett in eine Datei schreiben. Bei größeren Projekten entsteht so aber schnell Chaos.

Monolithisches Programm

In einem monolithischen Programm steht alles in einer Datei:

- Klassen
- Eingaben
- Berechnungen
- Ausgaben
- Hilfsfunktionen

Das funktioniert – aber:

  • Der Code wird unübersichtlich.
  • Fehler sind schwer zu finden.
  • Erweiterungen machen alles komplizierter.
  • Im Team bearbeiten alle dieselbe Datei und überschreiben sich gegenseitig die Änderungen.

Zum Nachlesen: Struktur eines sauberen Projekts

Statt alles in eine Datei zu schreiben, nutzt du mehrere Module:

projekt/
│
├── fahrzeug.py
├── auto.py
├── motorrad.py
└── main.py
  • eine Klasse pro Datei
  • Importe verbinden die Module
  • main.py startet das Programm

Später kommt zu jedem Modul eine Testdatei mit demselben Namen und dem Vorsatz test_ dazu, z. B. test_auto.py neben auto.py (Seite 5.3).

Zum Nachlesen: Wie verbindet man die Dateien?

Damit Python weiß, dass es Klassen aus anderen Dateien nutzen soll, verwendet man Importe. Beispiel in auto.py:

from fahrzeug import Fahrzeug

Das bedeutet:

  • Python sucht die Datei fahrzeug.py (im selben Ordner).
  • Dort wird die Klasse Fahrzeug geladen.
  • Die Klasse kann nun verwendet werden.

Es gibt zwei Schreibweisen: from fahrzeug import Fahrzeug holt nur den Namen Fahrzeug, du schreibst danach Fahrzeug("VW"). import fahrzeug holt das ganze Modul, du schreibst dann fahrzeug.Fahrzeug("VW"). Ein Modul wird pro Programmlauf nur einmal ausgeführt, auch wenn es mehrere andere Module importieren.

Jedes Modul kann man direkt starten oder importieren – und beim Import führt Python den Code auf oberster Ebene aus. Damit ein Selbsttest in fahrzeug.py nicht bei jedem Import mitläuft, steht er unter if __name__ == "__main__":. Im Video startest du nacheinander fahrzeug.py, main.py und auto.py. Achte in der Tabelle rechts darauf, welchen Wert __name__ jeweils hat, und auf die Reihenfolge, in der die Module geladen werden.

Zum Nachlesen: Warum braucht man main.py?

Wenn du mit mehreren Python-Dateien arbeitest, ist jede Datei zunächst ein eigenes Modul. Ein Modul kann

  • direkt gestartet werden
  • oder von einer anderen Datei importiert werden.

Das Problem

Angenommen, in einer Datei steht einfach:

print("Programm startet")

Dann passiert Folgendes:

  • Startest du die Datei direkt, erscheint die Ausgabe.
  • Importierst du die Datei, erscheint die Ausgabe ebenfalls.

Das bedeutet: Code wird beim Import automatisch ausgeführt. Genau das wollen wir bei Klassen-Dateien nicht.

Die Lösung: kontrollierter Programmeinstieg

Deshalb nutzt man in Python folgende Struktur:

def main():
    print("Programm startet")

if __name__ == "__main__":
    main()

Was passiert hier?

__name__ ist eine besondere Variable, die Python automatisch setzt.

  • Wird die Datei direkt gestartet, hat __name__ den Wert "__main__".
  • Wird die Datei importiert, hat __name__ den Namen des Moduls (z. B. "fahrzeug").
Hinweis: Warum ist das wichtig?

Beim Import sollen nur Klassen und Funktionen geladen werden – aber kein Programm automatisch starten. Diese Abfrage verhindert genau das.

Ausgangssituation: Die Klassen Fahrzeug und Auto sollen in eigenen Dateien stehen. main.py erzeugt zwei Objekte und gibt ihre Beschreibung aus. Alle drei Dateien liegen im selben Ordner.

# fahrzeug.py
class Fahrzeug:
    def __init__(self, marke: str):
        self.marke = marke

    def beschreibung(self) -> str:
        return f"Fahrzeug der Marke {self.marke}"

    print(Fahrzeug("Test").beschreibung())

from fahrzeug import Fahrzeug

class Auto(Fahrzeug):
    def __init__(self, marke: str, tueren: int):
        super().__init__(marke)
        self.tueren = tueren

    def beschreibung(self) -> str:
        return super().beschreibung() + f" mit {self.tueren} Türen"
# main.py  (Controller, View über print)
from fahrzeug import Fahrzeug
from auto import Auto

def main():
    fuhrpark = [Fahrzeug("Simson"), Auto("VW", 5)]
    for f in fuhrpark:
        print(f.beschreibung())     # polymorpher Aufruf

if __name__ == "__main__":
    main()

  2. Abhängigkeit durch Import ausdrücken: Auto erbt von Fahrzeug, also steht in auto.py ganz oben from fahrzeug import Fahrzeug. Warum: Ohne Import kennt Python in auto.py den Namen Fahrzeug nicht und meldet NameError.
  3. Selbsttest schützen: Die Testzeile in fahrzeug.py steht unter if __name__ == "__main__":. Warum: Startest du fahrzeug.py direkt, siehst du „Fahrzeug der Marke Test“. Beim Import durch auto.py oder main.py ist __name__ dort "fahrzeug", die Zeile wird übersprungen.
  4. Ablauf von main.py verfolgen: Python führt zuerst fahrzeug.py aus (Klasse wird definiert, keine Ausgabe), dann auto.py. Dessen Import von fahrzeug löst nichts Neues aus, weil das Modul schon geladen ist. Danach läuft main(): Die Schleife ruft für jedes Objekt beschreibung() auf – beim Auto die überschriebene Fassung.

Zum Nachlesen: MVC – Model View Controller

Eine bekannte Softwarearchitektur ist das MVC-Modell.

  • Model: enthält die Daten und die Logik (z. B. Klassen)
  • View: stellt Daten dar (z. B. grafische Oberfläche oder Konsolenausgabe)
  • Controller: steuert den Ablauf und verarbeitet Eingaben

Was wir im Projekt umsetzen – und was nicht

Im Projekt am Ende dieses Kurses (Seiten 5.5 und 5.6) verwendest du eine vereinfachte MVC-Struktur:

  • Model: deine Klassen (z. B. Fahrzeuge)
  • Controller: main.py
  • View: Konsolenausgabe mit print(), gesammelt in einem eigenen Modul (z. B. ansicht.py)

Eine grafische Benutzeroberfläche (GUI) entwickeln wir bewusst nicht.

Hinweis: Warum keine GUI?

Die Entwicklung grafischer Oberflächen gehört zum sogenannten Frontend-Bereich. In diesem Projekt liegt der Schwerpunkt auf Modellierung, objektorientierter Struktur, sauberer Architektur und Wiederverwendbarkeit. Die Benutzeroberfläche ist hier zweitrangig.

Beispiel 2 komplex Klassensprecherwahl nach MVC – mit Falle und Sonderfall

Ausgangssituation: Für die Klassensprecherwahl soll ein Programm die Stimmen auszählen. Kandidaten sind Ella, Jonas und Mats. Jede Stimme wird als Name eingetippt, eine leere Eingabe beendet die Wahl. Falsch geschriebene Namen zählen als ungültig. Haben zwei Personen gleich viele Stimmen und liegen vorn, ist eine Stichwahl nötig.

Ein erster Entwurf der Klasse enthielt diese Methode:

    def stimme_abgeben(self, name: str) -> None:
        if name in self.__stimmen:
            self.__stimmen[name] += 1
        else:
            print("ungültige Stimme")       # Ausgabe im Model

Das Team verteilt das Programm auf drei Module:

# wahl.py  (Model)
class Wahl:
    def __init__(self, kandidaten: list[str]):
        self.__stimmen: dict[str, int] = {}
        for name in kandidaten:
            self.__stimmen[name] = 0
        self.__ungueltig = 0

    def stimme_abgeben(self, name: str) -> bool:
        if name in self.__stimmen:
            self.__stimmen[name] += 1
            return True
        self.__ungueltig += 1
        return False

    def get_kandidaten(self) -> list[str]:
        return list(self.__stimmen)

    def stimmen(self, name: str) -> int:
        return self.__stimmen[name]

    def get_ungueltig(self) -> int:
        return self.__ungueltig

    def gewinner(self) -> str | None:
        hoechste = max(self.__stimmen.values())
        beste = []
        for name in self.__stimmen:
            if self.__stimmen[name] == hoechste:
                beste.append(name)
        if len(beste) == 1:
            return beste[0]
        return None          # Gleichstand: Stichwahl nötig
# ansicht.py  (View)
from wahl import Wahl

def zeige_ergebnis(wahl: Wahl) -> None:
    print("Ergebnis der Klassensprecherwahl")
    for name in wahl.get_kandidaten():
        print(f"  {name:<10}{wahl.stimmen(name):>3}")
    print(f"  {'ungültig':<10}{wahl.get_ungueltig():>3}")
    sieger = wahl.gewinner()
    if sieger is None:
        print("Gleichstand – Stichwahl nötig")
    else:
        print(f"Gewählt ist {sieger}.")
# main.py  (Controller)
from wahl import Wahl
from ansicht import zeige_ergebnis

def main() -> None:
    wahl = Wahl(["Ella", "Jonas", "Mats"])
    eingabe = input("Stimme (leer = Ende): ")
    while eingabe != "":
        if not wahl.stimme_abgeben(eingabe):
            print("ungültige Stimme")
        eingabe = input("Stimme (leer = Ende): ")
    zeige_ergebnis(wahl)

if __name__ == "__main__":
    main()
  1. Falle im Entwurf erkennen: Der erste Entwurf gibt im Model mit print aus und liefert nichts zurück. Warum das schlecht ist: Der Controller erfährt nicht, ob die Stimme gezählt wurde. Und wer die Klasse später in einer App mit Bildschirm benutzt, bekommt Meldungen in eine Konsole, die niemand sieht.
  2. Model mit Rückgabewert: stimme_abgeben gibt jetzt True oder False zurück und zählt ungültige Stimmen selbst mit. Warum: Das Model kennt die Regeln (wer ist Kandidat?), die Meldung „ungültige Stimme“ formuliert der Controller. So lässt sich die Klasse auch ohne Tastatur prüfen: Wahl(["Ella", "Jonas", "Mats"]).stimme_abgeben("ella") liefert False, denn Python unterscheidet Groß- und Kleinschreibung.
  3. Sonderfall Gleichstand im Model lösen: gewinner() sammelt alle Namen mit der höchsten Stimmenzahl. Nur wenn es genau einer ist, wird er zurückgegeben, sonst None. Warum im Model: Ob jemand gewählt ist, ist eine Regel der Wahl, keine Frage der Darstellung. Der Rückgabetyp str | None zwingt die View, den Fall zu behandeln.
  4. View nur für die Darstellung: ansicht.py fragt die Daten über öffentliche Methoden ab und formatiert sie. {name:<10} füllt den Namen links auf 10 Zeichen auf, {…:>3} setzt die Zahl rechtsbündig in 3 Stellen. Warum: Die Darstellung lässt sich ändern, ohne wahl.py anzufassen.
  5. Importrichtung prüfen: main.py importiert Model und View, ansicht.py importiert das Model, wahl.py importiert nichts. Warum: Das Model hängt von niemandem ab. Würde es umgekehrt die View importieren, wäre es nicht mehr ohne sie benutzbar.
  6. Ablauf an einer Eingabe: Eingaben Ella, Mats, Ella, Mats, Lisa und dann leer. „Lisa“ ist kein Kandidat, also False und die Meldung. Am Ende haben Ella und Mats je 2 Stimmen.

Ergebnis (Konsole beim Start von main.py):

Stimme (leer = Ende): Ella
Stimme (leer = Ende): Mats
Stimme (leer = Ende): Ella
Stimme (leer = Ende): Mats
Stimme (leer = Ende): Lisa
ungültige Stimme
Stimme (leer = Ende):
Ergebnis der Klassensprecherwahl
  Ella        2
  Jonas       0
  Mats        2
  ungültig    1

Kontrolle: Mit einer weiteren Stimme für Ella vor der leeren Eingabe lautet die letzte Zeile „Gewählt ist Ella.“ (Ella 3, Mats 2). Die Summe aller Stimmen (gültig + ungültig) ist gleich der Zahl der nicht leeren Eingaben.

Zusammenfassung

Größere Programme verteilt man auf Module: eine Klasse pro Datei, verbunden mit from modul import Name oder import modul. Beim Import führt Python den Code eines Moduls einmal aus; was nur beim direkten Start laufen soll, steht unter if __name__ == "__main__":. Nach MVC enthält das Model Daten und Logik ohne print und input, die View stellt dar, der Controller (main.py) steuert Eingaben und Ablauf. Importiert wird nur in eine Richtung: Controller → View und Model, View → Model; das Model importiert nichts.

Das Wichtigste

OOP macht Programme strukturierbar, erweiterbar und wartbar. Genau das brauchst du bei größeren Projekten.

main.py steuert den Ablauf.
Klassen-Dateien enthalten nur die Logik.
if __name__ == "__main__": sorgt dafür, dass ein Programm nur beim direkten Start ausgeführt wird.

MVC trennt Logik (Model), Darstellung (View) und Ablaufsteuerung (Controller). Dadurch bleibt Software übersichtlich, und einzelne Teile lassen sich austauschen – z. B. die Konsolenausgabe gegen eine grafische Oberfläche, ohne die Klassen zu ändern.
Faustregel: Im Model steht kein print und kein input. Methoden des Models geben Ergebnisse mit return zurück; was davon wie angezeigt wird, entscheidet die View.

Grundaufgaben

Kurz geprüft 1: Zwei Schreibweisen AFB I

In der Datei zahlen.py steht die Klasse Bruch. In main.py im selben Ordner soll Bruch(1, 2) erzeugt werden. Gib beide möglichen Importzeilen an und jeweils, wie der Aufruf dann geschrieben wird. Was meldet Python, wenn die Importzeile ganz fehlt?

Lösung zeigen

from zahlen import Bruch → Bruch(1, 2). import zahlen → zahlen.Bruch(1, 2) (Modulname davor). Ohne Import kennt Python den Namen Bruch in main.py nicht und meldet NameError: name 'Bruch' is not defined.

Kurz geprüft 2: Welchen Wert hat __name__? AFB I

Gib an, welchen Wert __name__ innerhalb von auto.py hat, wenn du (a) auto.py direkt startest und (b) main.py startest. Warum erscheint beim direkten Start von auto.py keine Ausgabe?

Lösung zeigen

(a) "__main__", (b) "auto" – der Modulname. auto.py enthält nur einen Import und eine Klassendefinition, aber keinen Aufruf von print auf oberster Ebene. Beim Import von fahrzeug ist dort __name__ gleich "fahrzeug", der Selbsttest läuft also auch nicht.
