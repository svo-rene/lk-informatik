Wenn drei Leute gleichzeitig an einem Referat in einem Online-Dokument schreiben, sieht jeder sofort die Änderungen der anderen. Bei Programmen ist das gefährlich: Ein halb fertiger Code eines Teammitglieds legt das Programm für alle lahm, und niemand hat geprüft, ob die Änderung überhaupt stimmt. Softwareteams arbeiten deshalb anders: Jede Änderung entsteht zuerst abseits der gemeinsamen Fassung, eine zweite Person prüft sie, und erst dann wird sie übernommen. Genau so arbeitet ihr im Projekt – vollständig im Browser auf git.inf7.eu, ohne Installation.

Das kennst du schon aus 10.3 (Kurs „KI und Projektmanagement“): anmelden auf git.inf7.eu, Gruppenrepository anlegen und Mitarbeiter eintragen, Dateien hochladen und im Web-Editor ändern, gute Commit-Nachrichten, Historie und Diff lesen, Issues mit Aufgabenliste und das Board unter „Projekte“. Dort habt ihr alle direkt in main gespeichert und durch eigene Dateien verhindert, dass ein Upload die Arbeit eines anderen überschreibt. Neu sind hier Branches, Pull Requests, Reviews, das Mergen, der Commit-Graph und Merge-Konflikte.

Schritt 1: Wie kommt eine Änderung nach main?

Im Repository kopfrechentrainer setzt Ben ein Issue um, Mia macht das Review. Das Video zeigt den ganzen Weg als Folge von Tafelbildern: oben die Leiste Issue → Branch → PR → Review → Merge, darunter der Commit-Graph, rechts die wichtigsten Angaben im Browser. Achte darauf, wohin die Zeiger main und 3-auswertung nach jedem Commit zeigen und welche zwei Vorgänger der Merge-Commit hat. Die Knöpfe heißen im Browser je nach Version etwas anders – siehe Hinweis oben.

Zum Nachlesen: die neuen Begriffe

  • Branch (Zweig): eine eigene Entwicklungslinie mit eigenem Namen. Ein Branch zweigt von einem Commit ab; neue Commits auf dem Branch ändern main nicht. Ein Branch ist technisch nur ein Zeiger auf seinen neuesten Commit.
  • main: der Hauptbranch. Hier liegt immer die lauffähige, geprüfte Fassung.
  • Pull Request (PR): der Antrag „Bitte übernehmt die Commits meines Branches nach main“. Ein PR zeigt alle Änderungen als Diff und bietet Platz für Kommentare. In Forgejo teilen sich Issues und Pull Requests die Nummern: Gibt es Issue #3, bekommt der nächste PR z. B. #4.
  • Review (Code-Review): Eine zweite Person liest den Diff, kommentiert einzelne Zeilen und entscheidet: Zustimmen, Kommentieren oder Änderung anfordern.
  • Merge (Zusammenführen): Die Commits des Branches werden in main übernommen. Forgejo legt dabei in der Regel einen Merge-Commit an, der zwei Vorgänger (Eltern) hat: den letzten Commit von main und den letzten Commit des Branches.
  • Merge-Konflikt: Zwei Branches haben dieselbe Stelle derselben Datei unterschiedlich geändert. Git kann nicht entscheiden, welche Fassung gilt, und mergt nicht automatisch.

Zum Nachlesen: der Ablauf im Browser

Beispiel: Im Repository kopfrechentrainer soll Ben das Issue #3 „Runde mit Prozentwert auswerten“ umsetzen. Mia macht das Review.

Browser-Schritt 1: Issue übernehmen

Issue #3 öffnen, in der Seitenleiste bei „Zuständige“ „Mir selbst zuweisen“ wählen und die Karte im Board unter „Projekte“ nach „In Progress“ ziehen – wie in 10.3.

Browser-Schritt 2: Ändern und dabei einen neuen Branch anlegen

  1. Datei öffnen (z. B. runde.py) und auf den Stift klicken – oder für eine neue Datei „Datei hinzufügen ▾“ → „Neue Datei“ bzw. „Datei hochladen“.
  2. Ändern und unter „Vorschau der Änderungen“ prüfen, ob nur das Gewollte geändert ist.
  3. Im Kasten „Änderungen committen“ die Commit-Nachricht mit Issue-Nummer schreiben, z. B. #3 Runde: richtige Antworten zählen.
  4. Nicht „Direkt in den Branch ‚main‘ einchecken“, sondern „Einen neuen Branch für diesen Commit erstellen und einen Pull-Request starten.“ wählen.
  5. Es erscheint ein Feld für den Branch-Namen. Statt des Vorschlags (z. B. …-patch-1) schreibst du Issue-Nummer und Stichwort: 3-auswertung (Kleinbuchstaben, Bindestriche, keine Umlaute).
  6. „Änderungen committen“. Forgejo legt den Branch an, speichert den Commit dort und öffnet das Formular für einen neuen Pull Request.

Browser-Schritt 3: Den Pull Request anlegen

  1. Oben steht der Vergleich: Ziel main ← Quelle 3-auswertung. Darunter siehst du den Diff.
  2. Titel: #3 Runde mit Prozentwert auswerten.
  3. Beschreibung: was geändert wurde, wie es getestet ist, und die Zeile Schließt #3 (oder englisch closes #3). Dann wird das Issue beim Merge in der Regel automatisch geschlossen – kontrolliert, ob es geklappt hat.
  4. In der Seitenleiste bei „Reviewer“ Mia eintragen (sonst im Kommentar mit @mia… erwähnen).
  5. „Pull-Request erstellen“.

Browser-Schritt 4: Weitere Commits auf denselben Branch

Der PR ist erst ein Vorschlag. Weitere Änderungen gehören auf denselben Branch, dann erscheinen sie automatisch im PR:

  1. Auf der Startseite des Repositorys oben links in der Branch-Auswahl von main auf 3-auswertung wechseln.
  2. Jetzt erst die Datei öffnen bzw. hochladen und ändern.
  3. Im Kasten „Änderungen committen“ steht jetzt „Direkt in den Branch ‚3-auswertung‘ einchecken.“ – genau das ist richtig.

Häufigster Fehler: Man vergisst den Wechsel in der Branch-Auswahl und legt beim nächsten Speichern einen zweiten Branch mit einem zweiten PR an. Dann den überzähligen PR schließen und die Änderung auf dem richtigen Branch wiederholen.

Browser-Schritt 5: Review

  1. Mia öffnet den PR (Reiter „Pull-Requests“) und dort die Ansicht der geänderten Dateien.
  2. Mit dem + neben einer Zeilennummer schreibt sie einen Kommentar genau zu dieser Zeile: Zeile, Problem, Vorschlag, z. B. „Z. 14: Bei einer leeren Runde teilst du durch 0. Vorschlag: bei 0 Aufgaben 0 zurückgeben und dafür einen Test ergänzen.“
  3. Zum Schluss schickt sie das Review ab und wählt Zustimmen (alles gut), Kommentieren (Fragen, Kleinigkeiten) oder Änderung anfordern (so nicht mergen).
  4. Ben antwortet auf Kommentare, korrigiert auf demselben Branch (Browser-Schritt 4) und bittet um ein neues Review.

Ein gutes Review prüft: Erfüllt der Code die Akzeptanzkriterien des Issues? Gibt es Tests, auch für Grenzwerte, und laufen sie? Sind Kapselung und MVC eingehalten (kein print/input im Model)? Sind Namen und Typhinweise verständlich? Kommentare sind sachlich und konkret – kritisiert wird der Code, nicht die Person.

Browser-Schritt 6: Mergen und aufräumen

  1. Nach der Freigabe klickt Ben unten im PR auf den Merge-Knopf (Einstellung „Merge-Commit erstellen“) und bestätigt.
  2. Danach bietet Forgejo an, den Branch zu löschen: „Branch löschen“. Der Branch ist nur noch ein überflüssiger Zeiger, die Commits bleiben in main erhalten.
  3. Karte im Board nach „Done“, Issue geschlossen? Wenn nicht, von Hand schließen.
Beispiel 1 einfach Ein Pull Request vom Issue bis zum Merge

Ausgangssituation: Repository kopfrechentrainer, Gruppe Ben und Mia. In main liegt nur der Commit 1a2b3c4 „Grundgerüst Kopfrechentrainer“ mit aufgabe.py und einem leeren runde.py. Issue #3: „Als Schüler möchte ich nach einer Runde sehen, wie viel Prozent ich richtig hatte, um meinen Fortschritt zu verfolgen.“ Ben übernimmt.

  1. Branch beim Speichern anlegen: Ben öffnet runde.py, schreibt die Klasse Runde mit antworten(), Nachricht #3 Runde: richtige Antworten zählen, Option „neuen Branch … Pull-Request“, Name 3-auswertung. Warum: main bleibt unberührt, solange niemand geprüft hat.
  2. PR anlegen: Titel #3 Runde mit Prozentwert auswerten, Beschreibung „Neue Klasse Runde; Tests folgen. Schließt #3“, Reviewer Mia. Forgejo vergibt die Nummer #4, weil #3 schon das Issue ist. Warum gleich anlegen: Mia sieht früh, woran Ben arbeitet, und kann Fragen stellen.
  3. Zweiter Commit auf demselben Branch: Ben wechselt in der Branch-Auswahl auf 3-auswertung, lädt runde.py mit der Methode prozent() und test_runde.py hoch, Nachricht #3 Runde: Prozent auf ganze Zahl gerundet, „Direkt in den Branch ‚3-auswertung‘ einchecken“. Warum: Der Commit erscheint automatisch im selben PR.
  4. Review: Mia lädt beide Dateien herunter, startet test_runde.py in Thonny (alle grün), kommentiert eine Zeile („Z. 12: Name r ist unklar, Vorschlag richtige“) und wählt danach Zustimmen, weil der Name kein Fehler ist. Warum Tests selbst starten: Der Reviewer verlässt sich nicht auf die Aussage „läuft bei mir“.
  5. Mergen: Mia hat zugestimmt, der Hinweis betrifft nur einen Namen. Ben antwortet im PR „Lege ich als neues Issue an“ (damit es nicht vergessen wird), klickt auf den Merge-Knopf und dann auf „Branch löschen“. Wäre der Hinweis ein Fehler gewesen, hätte er ihn vorher mit einem weiteren Commit auf demselben Branch behoben. Issue #3 wird durch „Schließt #3“ geschlossen, die Karte wandert nach „Done“.

Ergebnis: Der Commit-Graph sieht aus wie in Schritt 2: zwei Commits auf dem Branch, ein Merge-Commit e5f0c21 auf main mit den Eltern 1a2b3c4 und 9b1d7a2.

Kontrolle: In der Commit-Liste steht kein Commit von Ben direkt auf main außer dem Merge-Commit; im PR #4 sind Mias Kommentar und ihre Freigabe dokumentiert. Das ist später der Nachweis für Bens Anteil und für Mias Review.

Schritt 2: Den Commit-Graph lesen

Der Commit-Graph zeigt, was im Repository passiert ist: wer wann abgezweigt ist, was gemergt wurde und wo die Branch-Zeiger stehen. Im Video siehst du Bens Verlauf aus Schritt 1 in zwei Darstellungen – waagerecht wie auf Papier und senkrecht wie in Forgejo. Achte darauf, worauf die Pfeile zeigen, woran man eine Abzweigung und einen Merge-Commit erkennt und was beim Löschen eines Branches verschwindet.

Zum Nachlesen: den Commit-Graph lesen

Ein Commit-Graph zeigt Commits als Punkte und ihre Vorgänger als Linien. Auf git.inf7.eu findest du ihn über „… Commits“ in der Graph-Ansicht; dort steht – wie bei git log --graph – der neueste Commit oben. Nach Bens Merge sieht der Verlauf so aus:

*   e5f0c21 (main) Merge pull request '#3 Runde mit Prozentwert auswerten' (#4) from 3-auswertung into main
|\
| * 9b1d7a2 #3 Runde: Prozent auf ganze Zahl gerundet
| * 4c8e6f0 #3 Runde: richtige Antworten zählen
|/
* 1a2b3c4 Grundgerüst Kopfrechentrainer

Auf Papier zeichnet man denselben Verlauf meist waagerecht. Die Zeit läuft nach rechts, jede Linie verbindet einen Commit mit seinem Nachfolger, der Zeiger main steht am neuesten Commit:

main           1a2b3c4 ──────────────────────────────── e5f0c21   ◀ main
                      \                                 /
3-auswertung           4c8e6f0 ──────── 9b1d7a2 ───────
  • Eine Abzweigung (|/ bzw. die Linie nach unten) zeigt, von welchem Commit ein Branch ausging – hier von 1a2b3c4.
  • Ein Merge-Commit (|\) hat zwei Eltern – hier 1a2b3c4 und 9b1d7a2.
  • Branch-Zeiger stehen in Klammern hinter dem Commit, auf den sie zeigen. Nach dem Löschen von 3-auswertung steht dort nur noch (main).
  • Ein Commit, der direkt in main gespeichert wurde, liegt auf der linken Linie und hat keinen Pull Request – im Team ein Regelverstoß.

Im Video zeigen die Pfeile vom Commit auf seinen Vorgänger (Elter), so wie Git die Verbindung speichert. Auf Papier genügen Linien wie oben.

Danach: Aufgabe 5.4.1 – einen Verlauf lesen und zeichnen.

Schritt 3: Merge-Konflikte erkennen, lösen und vermeiden

Ben und Mia fügen in main.py an derselben Stelle je einen Menüpunkt ein. Bens PR wird zuerst gemergt – danach kann Mias PR nicht mehr automatisch gemergt werden. Im Video siehst du, warum, wie Git die beiden Fassungen mit Konfliktmarkierungen in die Datei schreiben würde und wie Mia das im Browser löst. Achte darauf, was zwischen <<<<<<<, ======= und >>>>>>> steht und warum man nicht einfach eine Fassung übernimmt.

Zum Nachlesen: Merge-Konflikte – und wie ihr sie vermeidet

Git führt Änderungen zeilenweise zusammen. Ändert Branch A die Zeilen 3–5 und Branch B die Zeilen 20–22 derselben Datei, übernimmt Git beides automatisch. Haben aber beide Branches dieselben Zeilen unterschiedlich geändert (oder die eine Seite die Zeilen gelöscht, die andere sie geändert), entsteht ein Konflikt. Git schreibt dann beide Fassungen mit Markierungen in die Datei:

<<<<<<< main
    print("3 – Bestenliste")
=======
    print("3 – Statistik")
>>>>>>> 10-menue-statistik

Oben steht die Fassung des einen, unten die des anderen Branches. Ein Mensch muss entscheiden, was gilt, die Markierungen entfernen und das Ergebnis committen. Auf git.inf7.eu zeigt der PR dann einen Hinweis auf Konflikte, und der Merge-Knopf ist gesperrt. Im Browser lässt sich ein Konflikt nur umständlich lösen (Beispiel 2).

Beispiel 2 komplex Zwei Pull Requests ändern dieselbe Zeile – Konflikt erkennen, lösen, künftig vermeiden

Ausgangssituation: In main (Commit 5b7e0d4) enthält main.py dieses Menü:

def zeige_menue() -> None:
    print("1 – Neue Runde")
    print("2 – Einstellungen")
    print("0 – Ende")

Am Montag legen Ben (Issue #7, Branch 7-menue-bestenliste) und Mia (Issue #10, Branch 10-menue-statistik) beide von 5b7e0d4 aus einen Branch an. Beide fügen hinter Zeile 3 eine neue Zeile ein: Ben print("3 – Bestenliste"), Mia print("3 – Statistik"). Bens PR #9 wird am Dienstag gemergt. Mias PR #11 zeigt danach: Konflikte, Merge nicht möglich.

main                 5b7e0d4 ─────────────────────── M   ◀ main
                        |  \                         /
7-menue-bestenliste     |   6d1c8e2 ────────────────        (PR #9, gemergt)
                         \
10-menue-statistik        8e4a2f9   ◀ 10-menue-statistik     (PR #11, Konflikt)
  1. Ursache erkennen: Beide Branches gehen von 5b7e0d4 aus und haben an derselben Stelle verschiedene Zeilen eingefügt. Für Mias PR vergleicht Git drei Fassungen: den gemeinsamen Vorgänger 5b7e0d4, das aktuelle main (mit Bens Zeile) und Mias Branch. Weil beide Seiten dieselbe Stelle geändert haben, entscheidet Git nicht selbst. Warum es Ben nicht traf: Als Bens PR gemergt wurde, hatte sich main seit der Abzweigung nicht geändert.
  2. Was Git in die Datei schreiben würde: 
    def zeige_menue() -> None:
    print("1 – Neue Runde")
    print("2 – Einstellungen")
<<<<<<< main
    print("3 – Bestenliste")
=======
    print("3 – Statistik")
>>>>>>> 10-menue-statistik
    print("0 – Ende")
    Die Zeilen ohne Änderung stehen nur einmal da. Warum das hilft: Man sieht genau, wo sich die beiden Fassungen widersprechen.
  3. Inhaltlich entscheiden: Das Menü soll beides anbieten: 3 – Bestenliste und 4 – Statistik. Eine der beiden Fassungen einfach zu übernehmen, wäre falsch – dann fehlte ein Menüpunkt.
  4. Im Browser lösen: Mia wechselt in der Branch-Auswahl auf main (dort ist Bens Zeile schon drin), öffnet main.py mit dem Stift, ergänzt print("4 – Statistik") und speichert mit „neuen Branch … Pull-Request“ als 10-menue-statistik-2, Nachricht #10 Menü: Punkt 4 Statistik. Den alten PR #11 schließt sie mit dem Kommentar „ersetzt durch neuen PR wegen Konflikt mit #9“. Warum ein neuer Branch: Ihr alter Branch würde auch nach einer weiteren Änderung mit main kollidieren, weil er weiter von 5b7e0d4 ausgeht. Der neue Branch beginnt beim aktuellen main.
  5. Ursache abstellen: In der Retrospektive vereinbart die Gruppe: main.py hat je Sprint eine verantwortliche Person (in diesem Sprint Ben). Wer einen Menüpunkt braucht, schreibt ihn ins Issue, Ben trägt ihn ein. Warum: Mit eigenen Dateien je Person kann ein solcher Konflikt gar nicht erst entstehen.

Ergebnis: Das Menü enthält vier Einträge, main läuft, der Verlauf dokumentiert den geschlossenen PR #11 und den neuen PR.

Kontrolle: Der neue PR zeigt im Diff genau eine grüne Zeile und keine roten. Zeigt er rote Zeilen bei Bens Menüpunkt, wurde der neue Branch versehentlich nicht vom aktuellen main aus angelegt.

Danach: Aufgabe 5.4.2 – Pull Request und Review zu zweit üben (mit Konflikt), und Aufgabe 5.4.3 – ein Review schreiben.

Die Regeln für euer Projekt

Praxisbezug: Pull Requests im Berufsalltag

Alltag: Freie Software wie der Browser Firefox, die Programmiersprache Python oder Forgejo selbst entsteht über Pull Requests von Menschen auf der ganzen Welt. Jede Änderung wird vor der Übernahme von erfahrenen Leuten geprüft.

Beruf: In Softwarefirmen gilt fast überall „kein Merge ohne Review“. Der Hauptbranch ist technisch geschützt; ein PR braucht eine oder zwei Freigaben, und automatische Tests müssen grün sein. Wer gute Reviews schreibt – konkret, freundlich, mit Vorschlag – ist im Team sehr gefragt. Auch in der Ausbildung zur Fachinformatikerin bzw. zum Fachinformatiker für Anwendungsentwicklung gehört dieser Ablauf heute zum Alltag.

Zusammenfassung

Im Team entsteht jede Änderung auf einem eigenen Branch, der beim Speichern im Browser angelegt wird und nach Issue-Nummer und Stichwort heißt. Ein Pull Request beantragt die Übernahme nach main; eine andere Person reviewt den Diff, startet die Tests und stimmt zu, kommentiert oder fordert Änderungen an. Erst dann wird gemergt – dabei entsteht ein Merge-Commit mit zwei Eltern – und der Branch, der nur ein Zeiger ist, wird gelöscht. Im Commit-Graph sieht man Abzweigungen, Merge-Commits und die Branch-Zeiger. Ändern zwei Branches dieselben Zeilen, entsteht ein Merge-Konflikt: Ein Mensch entscheidet, was gilt. Besser ist es, Konflikte durch eigene Dateien je Person, kleine Pull Requests und Branches vom aktuellen main zu vermeiden.

Das Wichtigste

Feature-Branch-Ablauf: Issue → eigener Branch → Commits → Pull Request → Review durch eine andere Person → Merge nach main → Branch löschen.
main enthält nur geprüften, lauffähigen Code. Jede Änderung kommt über einen Pull Request dorthin.

Konflikte vermeiden ist besser als Konflikte lösen.

  • In jedem Sprint bearbeitet jede Person eigene Dateien: ihr Modul und die Testdatei daneben.
  • Gemeinsame Dateien (main.py, ansicht.py, README.md) haben je Sprint eine verantwortliche Person. Wünsche der anderen kommen als Kommentar ins Issue.
  • Kleine Pull Requests, schnell reviewen, schnell mergen. Ein Branch, der eine Woche lebt, sammelt Konflikte.
  • Jeden neuen Branch vom aktuellen main aus anlegen (Branch-Auswahl steht auf main).

Regel 1 – Nie direkt auf main. Jede Änderung entsteht auf einem eigenen Branch <issue-nr>-<stichwort>, z. B. 3-auswertung.

Regel 2 – Jede Änderung kommt als Pull Request. Eine andere Person der Gruppe reviewt sie (mindestens ein konkreter Kommentar oder eine Freigabe). Gemergt wird erst nach der Freigabe, danach wird der Branch gelöscht.

Regel 3 – Commit-Nachrichten beginnen mit der Issue-Nummer: #3 Runde: Prozent auf ganze Zahl gerundet.

Regel 4 – Eigene Dateien je Person und Sprint, gemeinsame Dateien mit einer verantwortlichen Person (Schritt 3).

Regel 5 – main läuft immer. Vor dem Pull Request laufen alle Tests fehlerfrei; wer reviewt, startet sie noch einmal.

Grundaufgaben

Kurz geprüft 1: Reihenfolge und Nummer AFB I

Bringe in die richtige Reihenfolge: Merge-Knopf klicken – Issue sich selbst zuweisen – Review mit „Zustimmen“ – Branch löschen – Speichern mit neuem Branch und Pull Request – Pull Request mit „Schließt #…“ anlegen. Im Repository gibt es schon die Issues #1 bis #6 und noch keinen PR. Welche Nummer bekommt der erste PR?

Lösung zeigen

Issue sich selbst zuweisen → Speichern mit neuem Branch und Pull Request → Pull Request mit „Schließt #…“ anlegen → Review mit „Zustimmen“ → Merge-Knopf klicken → Branch löschen. Der PR bekommt die Nummer #7, weil sich Issues und Pull Requests die Nummern teilen.

Kurz geprüft 2: Eltern und Zeiger AFB I

In main liegen die Commits P und danach Q. Von Q zweigt der Branch 8-hilfe ab, auf dem R und danach S entstehen. Dann wird der PR gemergt (Merge-Commit X). Welche Eltern hat X? Worauf zeigt 8-hilfe kurz vor dem Löschen, und welche Commits verschwinden beim Löschen des Branches?

Lösung zeigen

X hat die Eltern Q (letzter Commit von main) und S (letzter Commit des Branches). 8-hilfe zeigt auf S. Beim Löschen verschwindet nur der Zeiger, kein Commit – R und S sind über X weiter in main enthalten.
