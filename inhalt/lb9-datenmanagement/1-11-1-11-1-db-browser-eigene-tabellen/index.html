Bisher hast du mit DB Browser immer schon fertige Datenbanken importiert und darin Abfragen ausgeführt. Jetzt kennst du das ERM, das Relationenmodell und Primär- sowie Fremdschlüssel – Zeit, selbst eine eigene Datenbank von Grund auf zu bauen. Dabei lernst du drei Wege kennen, wie Daten in eine Tabelle gelangen: über die Oberfläche, über SQL-Befehle und per CSV-Import.

1. Neue Datenbank anlegen

Klicke in DB Browser für SQLite auf „Datei“ > „Neue Datenbank“. Vergib einen Dateinamen (z. B. verein.db) und einen Speicherort. Es öffnet sich automatisch der Dialog zum Anlegen der ersten Tabelle – den kannst du an dieser Stelle mit „Abbrechen“ schließen, wir legen die Tabellen gleich gezielt an.

2. Tabellen über die Oberfläche erstellen

Im Reiter „Datenbankstruktur“ klickst du auf „Tabelle erstellen“. Dort vergibst du einen Tabellennamen und fügst über „Feld hinzufügen“ die einzelnen Spalten mit Namen und Datentyp hinzu. Für den Primärschlüssel setzt du in der Zeile des entsprechenden Feldes das Häkchen bei „PK“. Daneben gibt es eigene Häkchen für „NN“ (NOT NULL), „AI“ (AUTOINCREMENT) und „U“ (UNIQUE).

Baue für die folgenden Aufgaben diese beiden Tabellen eines kleinen Sportvereins nach:

Tabelle Spalte Datentyp Besonderheit
Trainingsgruppen TrainingsgruppeID INTEGER Primärschlüssel
Bezeichnung TEXT
Trainer TEXT
Mitglieder MitgliedID INTEGER Primärschlüssel
Nachname TEXT
Vorname TEXT
Geburtsdatum TEXT
TrainingsgruppeID INTEGER Fremdschlüssel → Trainingsgruppen.TrainingsgruppeID

3. Tabellen per SQL erstellen

Die gleiche Struktur kannst du auch direkt im Reiter „SQL ausführen“ mit dem Befehl CREATE TABLE anlegen. Das ist schneller, wenn du die Struktur schon genau kennst, und zeigt dir, wie ein Fremdschlüssel mit REFERENCES auf eine andere Tabelle verweist.

Beispiel 1 einfach

Ausgangssituation: Die Tabellen Trainingsgruppen und Mitglieder aus Abschnitt 2 (1:n-Beziehung: eine Gruppe hat mehrere Mitglieder, ein Mitglied gehört zu höchstens einer Gruppe) sollen per SQL angelegt werden.


CREATE TABLE Trainingsgruppen (
    TrainingsgruppeID INTEGER PRIMARY KEY,
    Bezeichnung TEXT NOT NULL,
    Trainer TEXT
);

CREATE TABLE Mitglieder (
    MitgliedID INTEGER PRIMARY KEY,
    Nachname TEXT NOT NULL,
    Vorname TEXT NOT NULL,
    Geburtsdatum TEXT,
    TrainingsgruppeID INTEGER,
    FOREIGN KEY (TrainingsgruppeID) REFERENCES Trainingsgruppen (TrainingsgruppeID)
);
  1. Zuerst die Tabelle ohne Fremdschlüssel anlegen (Trainingsgruppen). Warum? Der Fremdschlüssel in Mitglieder verweist auf sie; die Zieltabelle sollte vorher existieren.
  2. Primärschlüssel festlegen: TrainingsgruppeID INTEGER PRIMARY KEY bzw. MitgliedID INTEGER PRIMARY KEY. Warum? Jeder Datensatz muss eindeutig ansprechbar sein; bei INTEGER PRIMARY KEY vergibt SQLite fehlende Werte selbst.
  3. Pflichtfelder mit NOT NULL markieren (Bezeichnung, Nachname, Vorname). Warum? Ein Mitglied ohne Namen wäre unbrauchbar; die Datenbank weist solche Zeilen ab.
  4. Fremdschlüssel auf der n-Seite anlegen: TrainingsgruppeID in Mitglieder mit FOREIGN KEY … REFERENCES Trainingsgruppen (TrainingsgruppeID). Warum auf der n-Seite? Jedes Mitglied hat höchstens eine Gruppe, also passt genau ein Wert in die Zeile.

Ergebnis: Im Reiter „Datenbankstruktur“ stehen zwei leere Tabellen: Trainingsgruppen mit 3 Spalten und Mitglieder mit 5 Spalten.

Kontrolle: Bei eingeschalteter Fremdschlüsselprüfung (siehe Hinweis) muss INSERT INTO Mitglieder (MitgliedID, Nachname, Vorname, TrainingsgruppeID) VALUES (1, 'Kühn', 'Ida', 99); mit FOREIGN KEY constraint failed scheitern, weil es die Gruppe 99 nicht gibt. Nach dem INSERT der Gruppe 1 (Abschnitt 4.2) klappt derselbe Befehl mit TrainingsgruppeID 1.

Hinweis: Wird der Fremdschlüssel wirklich geprüft?

SQLite selbst prüft Fremdschlüssel nur, wenn die Einstellung PRAGMA foreign_keys = ON gesetzt ist; ohne sie könntest du ohne Fehlermeldung eine TrainingsgruppeID eintragen, die es gar nicht gibt. DB Browser schaltet diese Prüfung beim Öffnen einer Datenbank standardmäßig ein. Kontrollieren kannst du das im Reiter „Pragmas bearbeiten“: Dort muss das Häkchen bei „Foreign Keys“ gesetzt sein. Im Reiter „SQL ausführen“ bringt der PRAGMA-Befehl dagegen oft nichts, weil DB Browser deine Befehle dort in einer Transaktion ausführt und SQLite die Einstellung innerhalb einer Transaktion ignoriert. Wenn du später mit Python (sqlite3) arbeitest, musst du PRAGMA foreign_keys = ON selbst nach dem Verbinden ausführen.

4. Drei Wege, Daten hinzuzufügen

4.1 Über die Oberfläche

Wechsle in den Reiter „Daten durchsuchen“, wähle oben die gewünschte Tabelle aus und klicke auf „Neuer Datensatz“. Du kannst die Werte dann direkt in der Tabelle eintippen.

4.2 Über SQL-Befehle

Wie schon bei CRUD gelernt, fügst du mit INSERT INTO Datensätze über den Reiter „SQL ausführen“ hinzu. 


INSERT INTO Trainingsgruppen (TrainingsgruppeID, Bezeichnung, Trainer)
VALUES (1, 'Bambini', 'Frau Weber');

4.3 Als CSV-Datei importieren

Wenn schon viele Datensätze in einer CSV-Datei vorliegen (z. B. aus einer Vereinsverwaltung exportiert), musst du sie nicht einzeln eintippen. Klicke auf „Datei“ > „Importieren“ > „Tabelle aus CSV-Datei“. Wähle die Datei aus und prüfe im Importdialog:

  • Ist das richtige Trennzeichen ausgewählt (Komma oder Semikolon)?
  • Ist „Spaltennamen in erster Zeile“ aktiviert, falls die CSV eine Kopfzeile hat?
  • Passen die automatisch erkannten Datentypen der Spalten?
Hinweis: Import in eine bestehende Tabelle

Trägst du im Importdialog als Tabellennamen den Namen einer Tabelle ein, die du schon per CREATE TABLE angelegt hast (inklusive Primär- und Fremdschlüssel), fragt DB Browser, ob die Daten in diese bestehende Tabelle eingefügt werden sollen. Bestätigst du das, gelten die Schlüsselregeln auch für die importierten Zeilen. Bei einem neuen Namen legt der Import eine neue Tabelle ohne Schlüssel an.

Die beiden Tabellen oben sind der Grundfall: eine 1:n-Beziehung, ein Fremdschlüssel. Das folgende Beispiel zeigt, wie eine m:n-Beziehung mit zusammengesetztem Primärschlüssel angelegt wird und worauf du beim Befüllen achten musst.

Beispiel 2 komplex

Ausgangssituation: Der Verein will zusätzlich speichern, welche Mitglieder an welchen Wettkämpfen teilgenommen haben und welchen Platz sie belegt haben. Aus der Modellierung (Seite 1.11) stammt:

Wettkaempfe(WettkampfID, Bezeichnung, Datum)
Teilnahmen(↑MitgliedID, ↑WettkampfID, Platz)
  1. Erst die Tabelle ohne Fremdschlüssel anlegen. 
    CREATE TABLE Wettkaempfe (
    WettkampfID INTEGER PRIMARY KEY,
    Bezeichnung TEXT NOT NULL,
    Datum TEXT NOT NULL
);
    Warum zuerst? Teilnahmen verweist auf sie. SQLite würde die umgekehrte Reihenfolge zwar dulden, viele andere Datenbanksysteme aber nicht – und die Reihenfolge „erst das Ziel, dann der Verweis“ braucht man beim Einfügen ohnehin.
  2. Den zusammengesetzten Primärschlüssel als eigene Zeile schreiben. 
    CREATE TABLE Teilnahmen (
    MitgliedID INTEGER,
    WettkampfID INTEGER,
    Platz INTEGER,
    PRIMARY KEY (MitgliedID, WettkampfID),
    FOREIGN KEY (MitgliedID) REFERENCES Mitglieder (MitgliedID),
    FOREIGN KEY (WettkampfID) REFERENCES Wettkaempfe (WettkampfID)
);
    Warum nicht zweimal PRIMARY KEY hinter die Spalten? Dann meldet SQLite table "Teilnahmen" has more than one primary key. Ein Primärschlüssel aus zwei Spalten ist ein Schlüssel und wird deshalb einmal am Ende angegeben.
  3. Daten in der richtigen Reihenfolge einfügen. Angenommen, die Mitglieder 1 und 2 existieren bereits: 
    INSERT INTO Wettkaempfe (WettkampfID, Bezeichnung, Datum)
VALUES (1, 'Stadtmeisterschaft', '2026-06-13');

INSERT INTO Teilnahmen (MitgliedID, WettkampfID, Platz)
VALUES (1, 1, 2), (2, 1, 1);
    Warum diese Reihenfolge? Eine Teilnahme an Wettkampf 1 darf erst gespeichert werden, wenn es Wettkampf 1 gibt.
  4. Die Schlüsselregeln testen. Führe die folgenden Befehle einzeln aus: 
    INSERT INTO Teilnahmen VALUES (99, 1, 3);   -- Mitglied 99 gibt es nicht
INSERT INTO Teilnahmen VALUES (1, 1, 4);    -- Mitglied 1 ist schon eingetragen
    Der erste scheitert mit FOREIGN KEY constraint failed (referenzielle Integrität), der zweite mit UNIQUE constraint failed: Teilnahmen.MitgliedID, Teilnahmen.WettkampfID (Primärschlüssel). Warum testen? So siehst du, dass die Datenbank die Regeln wirklich überwacht.
  5. Probe mit einer Abfrage. 
    SELECT m.Vorname, m.Nachname, w.Bezeichnung, t.Platz
FROM Teilnahmen t
JOIN Mitglieder m   ON t.MitgliedID = m.MitgliedID
JOIN Wettkaempfe w  ON t.WettkampfID = w.WettkampfID
ORDER BY t.Platz;
    Es erscheinen genau die zwei eingefügten Teilnahmen, Platz 1 zuerst.

Ergebnis: Die m:n-Beziehung ist als eigene Tabelle mit zwei Fremdschlüsseln umgesetzt, die zusammen den Primärschlüssel bilden. Die Datenbank verhindert Teilnahmen nicht vorhandener Mitglieder und doppelte Einträge.

Falle: Wird die Fremdschlüsselprüfung ausgeschaltet (Häkchen „Foreign Keys“ unter „Pragmas bearbeiten“ fehlt), läuft der erste Testbefehl ohne Fehler durch – die verwaiste Zeile fällt erst später auf.

Praxisbezug: Datenbanken für Vereine und kleine Betriebe

Viele Sportvereine, Arztpraxen oder Handwerksbetriebe verwalten Mitglieder, Termine und Aufträge in kleinen Datenbanken. Wer so etwas als Fachinformatiker*in für Anwendungsentwicklung oder in der Datenbankadministration aufbaut, legt zuerst die Struktur mit Schlüsseln an und übernimmt dann Altbestände per CSV-Import aus alten Excel-Listen – genau die drei Wege dieser Seite. Weil Mitgliederdaten personenbezogen sind, gehört nach DSGVO auch dazu, nur nötige Spalten anzulegen und die Datei vor fremdem Zugriff zu schützen.

Das Wichtigste

Ein Primärschlüssel muss eindeutig sein und darf keinen fehlenden Wert (NULL) enthalten. Das Häkchen bei „PK“ erzeugt in DB Browser nur PRIMARY KEY. Die automatische Hochzählung setzt erst das zusätzliche Häkchen „AI“ (AUTOINCREMENT), das nur bei INTEGER-Spalten möglich ist.

Achtung, SQLite-Besonderheit: Nur eine Spalte vom Typ INTEGER PRIMARY KEY ist garantiert nie NULL – lässt du den Wert weg, vergibt SQLite automatisch die nächste Nummer. Bei einem Primärschlüssel mit anderem Datentyp (z. B. TEXT) lässt SQLite aus historischen Gründen NULL-Werte zu. Setze dort zusätzlich „NN“ (NOT NULL).

Syntax für CREATE TABLE mit Primär- und Fremdschlüssel:
CREATE TABLE Tabellenname (
  Spalte1 Datentyp PRIMARY KEY,
  Spalte2 Datentyp,
  FremdschluesselSpalte Datentyp,
  FOREIGN KEY (FremdschluesselSpalte) REFERENCES ZielTabelle (ZielSpalte)
);
