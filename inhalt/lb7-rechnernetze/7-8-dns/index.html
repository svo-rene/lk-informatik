Du tippst www.tu-dresden.de in den Browser – aber Router können mit Namen nichts anfangen, sie brauchen IP-Adressen. Bevor die Webseite überhaupt angefragt wird, fragt dein Rechner deshalb im Hintergrund das „Telefonbuch des Internets“: das Domain Name System.

Namensauflösung

Namensauflösung ist der Vorgang, einen Domainnamen (z. B. „www.example.com“) in eine maschinenlesbare IP-Adresse (z. B. „192.0.2.1“ bei IPv4) umzuwandeln, mit der Netzwerkgeräte ein Ziel im Internet finden und erreichen. Die Namensauflösung ist eine typische Aufgabe der Anwendungsschicht und ermöglicht es, Webangebote zu nutzen, ohne sich komplizierte IP-Adressen merken zu müssen.

Domain Name System (DNS)

DNS ist ein dezentrales, hierarchisch aufgebautes System für die Namensauflösung im Internet. Es übersetzt menschenlesbare Domainnamen in IP-Adressen (und umgekehrt). Viele DNS-Server im Internet arbeiten zusammen, um Anfragen zu beantworten. Der Vorgang beginnt meist bei einem DNS-Resolver (z. B. dem des Internetanbieters oder dem Heimrouter), der die Anfrage stellvertretend für den Client an andere DNS-Server weitergibt, bis die zugehörige IP-Adresse gefunden ist. DNS-Anfragen laufen normalerweise über UDP auf Port 53, große Antworten über TCP Port 53.

Die DNS-Hierarchie

Ein vollständiger Domainname (FQDN, Fully Qualified Domain Name) wird von rechts nach links gelesen: www.example.de.

  • Root „.“ (der abschließende Punkt, meist weggelassen): Die Root-Server kennen die Server aller Top-Level-Domains.
  • Top-Level-Domain (TLD) „de“: Die TLD-Server (für .de betrieben von der DENIC in Frankfurt am Main) kennen die zuständigen Server jeder .de-Domain.
  • Second-Level-Domain „example“: Der autoritative Nameserver dieser Domain kennt die echten Einträge.
  • Subdomain bzw. Hostname „www“.

Man unterscheidet zwei Arten von Anfragen: Der Client stellt an den Resolver eine rekursive Anfrage („Bring mir die fertige Antwort“). Der Resolver fragt dann iterativ: Jeder Server antwortet entweder mit dem Ergebnis oder mit einem Verweis auf den nächsten zuständigen Server. Antworten werden für die im Eintrag angegebene Zeit (TTL) zwischengespeichert (Caching), damit nicht jede Anfrage bis zu den Root-Servern laufen muss.

Beispiel: ein IPv4-A-Record

Ein DNS-A-Record (Address Record) verknüpft einen Domainnamen mit seiner IPv4-Adresse. Ein vollständiger A-Record enthält folgende Elemente:

  • Domainname: der menschenlesbare Name (z. B. „www.example.com.“).
  • TTL (Time to Live): wie lange ein Resolver den Eintrag im Cache behalten darf, in Sekunden. Ein typischer Wert ist 86400 (24 Stunden).
  • Klasse: fast immer „IN“ für Internet.
  • Typ: hier „A“ für eine IPv4-Adresse.
  • IP-Adresse: die IPv4-Adresse, die dem Domainnamen zugeordnet ist (z. B. „192.0.2.1“).

So sieht der A-Record in der Zonendatei eines DNS-Servers aus:

www.example.com. 86400 IN A 192.0.2.1

Dabei ist „www.example.com.“ der Domainname, „86400“ die TTL in Sekunden, „IN“ die Klasse Internet, „A“ der Typ des Eintrags und „192.0.2.1“ die zugeordnete IPv4-Adresse.

Beispiel 1: Ein Name, eine Adresse einfach

Gibt ein Benutzer „www.example.com“ in seinen Webbrowser ein, sendet der Rechner eine DNS-Anfrage nach dem A-Record für „www.example.com“. Der DNS-Server antwortet mit der IPv4-Adresse „192.0.2.1“, und der Browser baut eine Verbindung zu dem Webserver auf, der die Webseite bereitstellt. In Filius entspricht das dem Eintrag gdp.de. A 3600 192.168.3.2 auf dem DNS-Server (→ 7.16).

Beispiel 2: Iterative Auflösung von www.gymnasium-beispiel.de komplex

Der Cache des Resolvers ist leer.

  1. Laptop → Resolver (FRITZ!Box bzw. Provider): „Welche IP hat www.gymnasium-beispiel.de?“ (rekursive Anfrage)
  2. Resolver → Root-Server: Antwort: „Weiß ich nicht, frag die Nameserver für .de.“ (Verweis mit NS-Einträgen)
  3. Resolver → TLD-Server .de: Antwort: „Frag den Nameserver ns1.hoster-beispiel.de, der ist für gymnasium-beispiel.de zuständig.“
  4. Resolver → autoritativer Nameserver ns1.hoster-beispiel.de: Antwort: www.gymnasium-beispiel.de. 3600 IN A 198.51.100.7
  5. Resolver → Laptop: 198.51.100.7. Der Resolver speichert die Antwort 3600 s (1 Stunde) im Cache.

Fragt eine Mitschülerin zehn Minuten später dieselbe Adresse beim selben Resolver an, antwortet er sofort aus dem Cache – ganz ohne Schritte 2 bis 4. Den Verweis auf die .de-Server hat er ohnehin noch viel länger gespeichert.

DNS over HTTPS (DoH)

Klassische DNS-Anfragen sind unverschlüsselt: Jeder im Netz kann mitlesen, welche Namen du auflöst, und Antworten könnten manipuliert werden. DNS over HTTPS (DoH) verbessert Datenschutz und Sicherheit, indem DNS-Anfragen und -Antworten verschlüsselt innerhalb von HTTPS übertragen werden. Das verhindert Überwachung und Manipulation durch Dritte. DoH nutzt dieselbe Portnummer wie normaler HTTPS-Verkehr (443); deshalb können Netzbetreiber DoH-Verkehr kaum von anderem Webverkehr unterscheiden oder gezielt blockieren.

Praxisbezug: „Das Internet ist kaputt“ – oder nur das DNS?

Alltag: Die FRITZ!Box arbeitet im Heimnetz als DNS-Resolver: Dein Handy fragt sie, und sie fragt weiter beim Provider. Fällt dieser DNS-Dienst aus, wirkt es, als sei „das Internet weg“, obwohl die Verbindung funktioniert. Ein ping 1.1.1.1 (IP-Adresse) klappt dann, ping www.tu-dresden.de (Name) nicht.

Beruf: Administratorinnen und Administratoren pflegen in Firmen und Schulen einen eigenen internen DNS-Server (z. B. für schule.local, vgl. Projektaufgabe P3) und die öffentlichen Einträge der Firmen-Domain beim Hoster. Ein häufiges Ticket nach einem Serverumzug: „Die neue Webseite ist bei manchen schon da, bei anderen noch nicht.“ Grund ist die TTL – alte Einträge stehen noch in den Caches der Resolver. Deshalb setzt man die TTL vor einem Umzug rechtzeitig herab.

Das Wichtigste

DNS – verteiltes, hierarchisches Verzeichnis, das Domainnamen in IP-Adressen übersetzt. Die Auflösung verläuft von der Root über die Top-Level-Domain bis zum autoritativen Nameserver der Domain. Resolver speichern Antworten für die Dauer der TTL zwischen.
