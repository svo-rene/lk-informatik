Schritt 3: Die binäre Suche Schritt für Schritt

Jetzt läuft das Programm zweimal: einmal mit der 23 (wird gefunden) und einmal mit der 13 (kommt nicht vor). Rechts siehst du die Zeiger in der Liste und unten den Aufrufstapel. Achte darauf, wie links und rechts zusammenrücken und was passiert, wenn sie sich überkreuzen.

Zum Nachlesen stehen Code, Ablauf und Testfälle in Beispiel 1:

Beispiel 1 einfach

Ausgangssituation: binäre Suche in einer sortierten Liste (nur eine Hälfte wird weiter untersucht)

def binaere_suche(liste, gesucht, links=0, rechts=None):
    if rechts is None:
        rechts = len(liste) - 1
    if links > rechts:                  # Basisfall: Bereich leer
        return -1
    mitte = (links + rechts) // 2       # Teilen
    if liste[mitte] == gesucht:
        return mitte
    elif gesucht < liste[mitte]:        # nur links weitersuchen
        return binaere_suche(liste, gesucht, links, mitte - 1)
    else:                               # nur rechts weitersuchen
        return binaere_suche(liste, gesucht, mitte + 1, rechts)

print(binaere_suche([2, 5, 8, 12, 16, 23, 38], 23))   # 5
  1. Erster Aufruf: links = 0, rechts = 6, mitte = (0 + 6) // 2 = 3. liste[3] = 12 ist kleiner als 23. Warum genügt die rechte Hälfte? Die Liste ist sortiert, also stehen alle Werte links von 12 ebenfalls unter 23.
  2. Zweiter Aufruf: links = 4, rechts = 6, mitte = 5. liste[5] = 23 → gefunden, Rückgabe 5.
  3. Ohne Treffer: Wird der Bereich leer (links > rechts), greift der Basisfall und liefert −1.

Schritt 4: Wie schnell ist die binäre Suche?

Jede Runde halbiert den Suchbereich. Wie viele Runden braucht man also höchstens – und wie viele Vergleiche die lineare Suche? Achte im Video darauf, was bei doppelt so langer Liste passiert, und auf die Voraussetzung, ohne die die binäre Suche falsche Ergebnisse liefert.

Zum Nachlesen: Beispiel 3 zählt die Vergleichsrunden beider Verfahren für eine und zwei Millionen Zahlen und misst die Laufzeit.

Beispiel 3 komplex

Ausgangssituation: Wie viel schneller ist die binäre Suche wirklich? Beide Suchverfahren zählen ihre Vergleichsrunden und werden mit time.perf_counter() gemessen. Der schlechteste Fall ist ein Wert, der größer als alle Listenelemente ist und deshalb nicht vorkommt.

import time

def lineare_suche(liste, gesucht):
    vergleiche = 0
    for i in range(len(liste)):
        vergleiche = vergleiche + 1
        if liste[i] == gesucht:
            return [i, vergleiche]
    return [-1, vergleiche]

def binaere_suche_iterativ(liste, gesucht):
    vergleiche = 0
    links = 0
    rechts = len(liste) - 1
    while links <= rechts:
        mitte = (links + rechts) // 2
        vergleiche = vergleiche + 1                      # eine Vergleichsrunde
        if liste[mitte] == gesucht:
            return [mitte, vergleiche]
        elif gesucht < liste[mitte]:
            rechts = mitte - 1
        else:
            links = mitte + 1
    return [-1, vergleiche]

for n in [1_000_000, 2_000_000]:
    liste = list(range(0, 2 * n, 2))        # n gerade Zahlen, sortiert
    gesucht = 2 * n                          # größer als alle: schlechtester Fall
    start = time.perf_counter()
    ergebnis = lineare_suche(liste, gesucht)
    t_lin = round((time.perf_counter() - start) * 1000, 3)   # in ms
    v_lin = ergebnis[1]
    start = time.perf_counter()
    ergebnis = binaere_suche_iterativ(liste, gesucht)
    t_bin = round((time.perf_counter() - start) * 1000, 3)
    v_bin = ergebnis[1]
    print(n, v_lin, t_lin, "ms", v_bin, t_bin, "ms")
  1. Vergleiche linear: Jedes Element wird angesehen, also 1 000 000 bzw. 2 000 000 Runden. Warum schlechtester Fall: Der gesuchte Wert kommt nicht vor.
  2. Vergleiche binär: Der Suchbereich halbiert sich in jeder Runde (1 000 000 → 500 000 → … → 1), bis er leer ist. Das ergibt ⌊log2 n⌋ + 1 Runden: 20 für eine Million und 21 für zwei Millionen. Warum nur eine Runde mehr? Die doppelte Liste ist nach einer Halbierung wieder so groß wie die alte.
  3. Laufzeit messen und auswerten: Beispielwerte eines Schulrechners: linear 61 ms bzw. 123 ms (Faktor ≈ 2 → O(n)), binär jeweils etwa 0,006 ms (praktisch unverändert → O(log n)). Die absoluten Zeiten schwanken, die Vergleichszahlen nicht.
  4. Falle Duplikate: binaere_suche_iterativ([1, 3, 3, 3, 5], 3) liefert [2, 1], lineare_suche dagegen [1, 2]. Beide Indizes sind „richtig“, aber die binäre Suche findet nicht unbedingt das erste Vorkommen.
  5. Preis der Geschwindigkeit: Die binäre Suche setzt eine sortierte Liste voraus. Muss erst sortiert werden, kostet das mehr als eine einzelne lineare Suche. Es lohnt sich erst, wenn oft in denselben Daten gesucht wird.

Ergebnis: Ausgabe 1000000 1000000 … 20 … und 2000000 2000000 … 21 …. Bei doppeltem n verdoppelt sich der Aufwand der linearen Suche, bei der binären Suche kommt nur eine Runde hinzu.

Schritt 5: Teilen, herrschen, kombinieren – das Maximum

Bei der binären Suche fällt nach dem Teilen eine Hälfte weg. Beim Maximum einer Liste werden beide Hälften gebraucht – hier siehst du alle drei Schritte von Divide and Conquer. Kurz erklärt wird das Slicing (liste[:mitte], liste[mitte:]). Achte im Aufrufbaum darauf, wie die Ergebnisse von unten nach oben kombiniert werden.

Zum Nachlesen – mit der Falle „leere Liste“, die nicht im Video vorkommt – steht alles in Beispiel 2:

Beispiel 2 komplex

Ausgangssituation: Maximum einer Liste mit allen drei Schritten

def maximum(liste):
    if len(liste) == 1:                 # Basisfall
        return liste[0]
    mitte = len(liste) // 2
    links = maximum(liste[:mitte])      # Teilen und rekursiv lösen
    rechts = maximum(liste[mitte:])
    if links > rechts:                # Kombinieren
        return links
    else:
        return rechts

print(maximum([7, 3, 19, 4, 11]))       # 19
  1. Teilen: mitte = 5 // 2 = 2 → [7, 3] und [19, 4, 11]. Warum //: Bei ungerader Länge ist die rechte Hälfte um eins größer, beide Teile sind aber nicht leer.
  2. Herrschen: maximum([7, 3]) liefert 7. maximum([19, 4, 11]) teilt weiter in [19] und [4, 11] und liefert 19.
  3. Kombinieren: 7 > 19? Nein → Ergebnis 19. Zurückgegeben wird also der größere der beiden Werte.
  4. Aufwand zählen: Jeder Kombinierschritt kostet einen Vergleich, und es gibt n − 1 davon (hier 4). Das ist genauso viel wie bei der linearen Suche nach dem Maximum. Warum lohnt sich Divide and Conquer hier nicht? Jedes Element muss ohnehin einmal angesehen werden. Das Halbieren spart nur dann Arbeit, wenn wie bei der binären Suche eine Hälfte wegfallen darf. Die Teillisten-Kopien mit liste[:mitte] kosten sogar zusätzlich Zeit und Speicher.
  5. Falle leere Liste: Für [] ist len = 0 ≠ 1, mitte = 0, und maximum([]) ruft sich mit derselben leeren Liste wieder auf → RecursionError. Abhilfe: if len(liste) == 0: return None als zusätzlicher Basisfall.

Ergebnis: 19 mit 4 Vergleichen. Die Rekursionstiefe beträgt nur ⌈log2 n⌉ + 1, hier 4 (längste Aufrufkette: [7, 3, 19, 4, 11] → [19, 4, 11] → [4, 11] → [11]).

Kurz geprüft 5: Drei Zahlen teilen AFB I

Wie teilt maximum die Liste [8, 2, 5]? Welche Teillisten entstehen insgesamt, und wie viele Vergleiche finden beim Kombinieren statt?

Lösung zeigen

mitte = 3 // 2 = 1 → [8] und [2, 5]; [2, 5] wird in [2] und [5] geteilt. Kombinieren: 2 > 5? Nein → 5; dann 8 > 5? Ja → 8. Zwei Vergleiche, also n − 1.

Anwendungen des Divide-and-Conquer-Prinzips

  • Sortieralgorithmen: Mergesort und Quicksort teilen eine Liste in kleinere Teillisten, sortieren diese rekursiv und setzen sie wieder zusammen.
  • Suchalgorithmen: Die binäre Suche in einer sortierten Liste oder in einem Suchbaum halbiert den Suchraum in jedem Schritt.
  • Rechnen mit großen Zahlen: Schnelles Potenzieren berechnet xn über xn/2 · xn/2 mit nur etwa log2 n Multiplikationen; das wird z. B. bei der RSA-Verschlüsselung genutzt.
  • Numerik: Das Bisektionsverfahren findet Nullstellen, indem es ein Intervall immer wieder halbiert.
  • Parallelisierung: Die Teilprobleme sind unabhängig voneinander und können auf mehreren Prozessorkernen gleichzeitig gelöst werden.
Hinweis: Nicht jede Rekursion ist Divide and Conquer

Die Tiefensuche (DFS) und die Breitensuche (BFS) in Graphen sind kein Divide and Conquer: Sie besuchen Knoten nacheinander, teilen das Problem aber nicht in unabhängige Teilprobleme, deren Lösungen anschließend kombiniert werden. Auch sum_recursion(n) aus 2.2.7 verkleinert das Problem nur um 1 und teilt es nicht auf.

Zusammenfassung

Divide and Conquer zerlegt ein Problem in kleinere Teilprobleme derselben Art, löst sie rekursiv und kombiniert die Teillösungen. Die binäre Suche nutzt das besonders wirksam: Weil die Liste sortiert ist, fällt in jeder Runde eine Hälfte weg, und sie braucht nur O(log n) statt O(n) Vergleiche. Beim Maximum müssen dagegen beide Hälften bearbeitet werden – dort spart das Teilen keine Vergleiche. Später nutzen Mergesort und Quicksort dasselbe Prinzip zum schnellen Sortieren.

Einschätzen: zurück zum Streamingdienst

Die Suche des Streamingdienstes soll einen Titel unter 100 Millionen Songs finden. Die binäre Suche braucht dafür nur etwa log2(108) ≈ 27 Vergleiche – aber nur in einer sortierten Liste. Sortieren kostet selbst etwas. Schätze ab:

  1. Eine einzige Suche: Lohnt es sich, vorher zu sortieren (mit Mergesort, etwa n · log2 n Vergleiche), oder ist die lineare Suche besser?
  2. Am Tag kommen 1 Million Suchanfragen. Wie viele Vergleiche sind es mit linearer Suche (im Mittel n / 2 pro Suche) und wie viele mit „einmal sortieren, dann binär suchen“?
Lösung zeigen

Eine Suche: linear höchstens 108 Vergleiche, Sortieren allein schon ≈ 2,7 · 109. Für eine einzige Suche lohnt sich Sortieren nicht. Eine Million Suchen: linear 106 · 5 · 107 = 5 · 1013 Vergleiche (mehrere Wochen Rechenzeit), sortiert 2,7 · 109 + 106 · 27 ≈ 2,7 · 109 (wenige Minuten). Einschätzen heißt also auch: Wie oft wird etwas gemacht? Einmalige Vorarbeit lohnt sich, wenn sie sich auf viele Anfragen verteilt (siehe auch Aufgabe 2.2.8.7).

Das Wichtigste

Divide and Conquer besteht aus drei Schritten:

  1. Teilen (Divide): Das Problem wird in kleinere Teilprobleme derselben Art zerlegt.
  2. Herrschen (Conquer): Die Teilprobleme werden rekursiv gelöst. Sind sie klein genug (Basisfall), werden sie direkt gelöst.
  3. Kombinieren (Combine): Die Teillösungen werden zur Lösung des Gesamtproblems zusammengesetzt.

Halbiert man das Problem in jedem Schritt, entstehen nur etwa log2 n Ebenen. Das ist der Grund für Laufzeiten wie O(log n) oder O(n log n).
