In den vorherigen Stunden hast du einfache Sortieralgorithmen wie Bubblesort und Insertionsort kennengelernt. Dabei wurde dir auch bewusst, dass diese Algorithmen bei größeren Datenmengen ineffizient sind.

Die Algorithmen, die du bisher kennengelernt hast, gehören zur Komplexitätsklasse O(n²). Für kleine Datenmengen ist das noch in Ordnung, bei großen Datenmengen dauert das Sortieren aber sehr lange. Daher braucht man effizientere Verfahren mit besserer Zeitkomplexität.

Mergesort ist ein effizienter Sortieralgorithmus mit einer garantierten Zeitkomplexität von O(n · log n) – im besten, mittleren und schlechtesten Fall. Er basiert auf dem Divide-and-Conquer-Prinzip und sortiert zuverlässig auch große Datenmengen.

Die Idee in einem Bild

Stell dir vor, 8 Personen sollen 8 Karten sortieren. Die erste Person teilt den Stapel und gibt je eine Hälfte an zwei andere weiter, diese teilen wieder – bis jede Person nur noch eine Karte hat. Eine einzelne Karte ist sortiert, da gibt es nichts zu tun. Jetzt geht es zurück: Je zwei Personen legen ihre sortierten Stapel zu einem sortierten Stapel zusammen, indem sie immer nur die beiden vorderen Karten vergleichen. Am Ende hält die erste Person alle 8 Karten sortiert in der Hand.

  • Teilen kostet keinen einzigen Vergleich – es wird nur halbiert.
  • Zusammenführen ist die eigentliche Arbeit – aber sie ist billig, weil beide Stapel schon sortiert sind.
  • Bei 8 Karten gibt es nur 3 Ebenen (8 → 4 → 2 → 1), bei 1 000 Karten nur 10, bei einer Million 20. Auf jeder Ebene wird jede Karte nur einmal angefasst.
Mit den Karten: Station Mergesort

Holt eure Zahlenkarten aus 2.2.1 wieder heraus. Es gelten die bekannten Regeln, mit einer Änderung: Jetzt ist eine zweite Reihe erlaubt – das ist der zusätzliche Speicher, den Mergesort braucht.

  1. Teilen: Teilt die 8 verdeckten Karten in zwei Hälften, gebt jede Hälfte weiter und teilt, bis jede Hälfte nur noch eine Karte hat.
  2. Zusammenführen: Zwei sortierte Stapel liegen verdeckt nebeneinander, die kleinste Karte vorn. Aufgedeckt werden nur die beiden vorderen Karten. Die kleinere kommt in die Ergebnisreihe (1 Strich V). Ist ein Stapel leer, kommt der Rest des anderen ohne Vergleich dahinter.

Hinweis: Divide and Conquer

Viele effiziente Algorithmen nutzen das Prinzip „Teile und herrsche“ (Divide and Conquer, siehe 2.2.8): Das Problem wird in kleinere Teilprobleme zerlegt, diese werden rekursiv gelöst, und die Teillösungen werden zu einer Gesamtlösung kombiniert.

Zum Verstehen: Warum ist Mergesort so viel schneller?

Auf jeder Ebene des Baums werden alle n Zahlen genau einmal in eine neue Liste übernommen, dafür reichen höchstens n Vergleiche. Die Zahl der Ebenen ist die Antwort auf die Frage „Wie oft kann ich n halbieren, bis 1 übrig bleibt?“, also log2 n. Zusammen sind das höchstens etwa n · log2 n Vergleiche.

def merge(links, rechts):
    ergebnis = []
    i = j = 0
    while i < len(links) and j < len(rechts):
        if links[i] <= rechts[j]:       # <= hält Mergesort stabil
            ergebnis.append(links[i])
            i = i + 1
        else:
            ergebnis.append(rechts[j])
            j = j + 1
    ergebnis.extend(links[i:])          # Rest anhängen
    ergebnis.extend(rechts[j:])
    return ergebnis

def mergesort(liste):
    if len(liste) <= 1:                 # Basisfall
        return liste
    mitte = len(liste) // 2
    links = mergesort(liste[:mitte])    # Teilen und Herrschen
    rechts = mergesort(liste[mitte:])
    return merge(links, rechts)         # Kombinieren

print(mergesort([38, 27, 43, 3, 9, 82, 10]))
# [3, 9, 10, 27, 38, 43, 82]

  2. Zusammenführen und Vergleiche zählen:

    Zum Vergleich: Bubblesort bräuchte ohne Abbruch 7 · 6 / 2 = 21 Vergleiche.
  3. Warum O(n · log n)? Es entstehen ⌈log2 7⌉ = 3 Ebenen. Auf jeder Ebene wird jedes Element höchstens einmal in eine neue Liste übernommen, das sind höchstens n Schritte pro Ebene.
  4. Stabilität: In merge steht <=. Bei gleichen Werten wird zuerst das Element aus der linken Teilliste genommen, und das stand ursprünglich weiter vorn. Mit < wäre Mergesort nicht mehr stabil.
  5. Bester und schlechtester Fall: Ein merge von a und b Elementen braucht mindestens min(a, b) und höchstens a + b − 1 Vergleiche. Die Gesamtzahl schwankt also nur in engen Grenzen. Auch eine bereits sortierte Liste kostet O(n log n), im Unterschied zu Insertionsort und Bubblesort mit Abbruch.
  6. Falle „sortiert die Funktion meine Liste?“: mergesort arbeitet mit Kopien (liste[:mitte]) und gibt eine neue Liste zurück. Nach zahlen = [3, 1, 2] und mergesort(zahlen) ist zahlen immer noch [3, 1, 2]. Richtig ist zahlen = mergesort(zahlen) (siehe call by sharing, 2.1.6).
  7. Rekursionstiefe: Nur etwa log2 n + 1 Aufrufe sind gleichzeitig offen, bei einer Million Elementen etwa 21. Anders als bei sum_recursion aus 2.2.7 droht kein RecursionError.
  8. Laufzeit messen:

        daten.append(random.randint(1, 10**6))

Wettrennen: Mergesort gegen die einfachen Verfahren

Alle Verfahren sortieren gleichzeitig dieselbe Liste. Ein Zeittakt ist ein Vergleich. Probiere verschiedene Startreihenfolgen aus. Mit dem Knopf unten zählt das Labor die Vergleiche für n = 8 bis 512 und zeichnet sie als Diagramm. Quicksort lernst du auf der nächsten Seite kennen.

Praxisbezug: Sortieren großer Datenmengen

Alltag: Wenn ein Streamingdienst Millionen Titel nach Beliebtheit ordnet oder deine Fotos-App Tausende Bilder nach Datum sortiert, stecken O(n · log n)-Verfahren dahinter. Mit O(n²) würde das Minuten statt Millisekunden dauern.

Beruf: Datenbanksysteme sortieren Tabellen, die nicht in den Arbeitsspeicher passen, mit „externem Mergesort“: Sie sortieren handliche Stücke im Arbeitsspeicher, schreiben sie auf die Festplatte und führen sie anschließend zusammen. Datenbankadministratorinnen und -administratoren beobachten solche Sortiervorgänge, um langsame Abfragen zu beschleunigen.

Zusammenfassung

Mergesort teilt die Liste so lange in Hälften, bis nur noch Listen mit höchstens einem Element übrig sind, und führt die sortierten Teillisten mit merge wieder zusammen. merge vergleicht dabei immer nur die vorderen Elemente zweier sortierter Listen und hängt am Ende den Rest an. Weil es etwa log2 n Ebenen gibt und auf jeder Ebene höchstens n Elemente bewegt werden, liegt Mergesort immer in O(n · log n). Er ist stabil, braucht aber zusätzlichen Speicher und gibt eine neue Liste zurück.

Das Wichtigste

Mergesort teilt die zu sortierende Liste in zwei Hälften, sortiert beide Hälften rekursiv und führt die sortierten Hälften anschließend zusammen (engl. merge). Eine Liste mit höchstens einem Element ist bereits sortiert (Basisfall).
Laufzeit: Es entstehen etwa log2 n Ebenen, und auf jeder Ebene werden beim Zusammenführen insgesamt n Elemente bewegt. Das ergibt O(n · log n). Mergesort braucht zusätzlichen Speicher für die Teillisten (O(n)).
