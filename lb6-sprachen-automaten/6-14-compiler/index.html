6.14 Compiler und Interpreter – von der Theorie zur Praxis

Einführung 2Übungen 5Vertiefung 1

Beim Umgang mit Programmiersprachen spielen Compiler und Interpreter eine zentrale Rolle. Sie sind dafür verantwortlich, den von Menschen geschriebenen Quellcode in eine für den Computer ausführbare Form zu übersetzen. Mit deinem Wissen über formale Sprachen, Grammatiken und Automaten kannst du nun verstehen, wie diese Übersetzung funktioniert.

1. Compiler vs. Interpreter – die Grundlagen

1.1 Compiler

Ein Compiler übersetzt den gesamten Quellcode einer höheren Programmiersprache in Maschinencode, bevor das Programm ausgeführt wird. Dieser übersetzte Code kann dann direkt von der Zielplattform ausgeführt werden (z. B. C, C++, Rust).

1.2 Interpreter

Ein Interpreter hingegen übersetzt und führt den Quellcode Anweisung für Anweisung aus. Er liest eine Anweisung, analysiert sie, führt sie aus und geht dann zur nächsten Anweisung über.

Hinweis: Mischformen mit Bytecode

Viele Sprachen verwenden eine Mischform: Java wird vom Compiler javac vollständig in Bytecode übersetzt, den die Java Virtual Machine (JVM) anschließend interpretiert bzw. zur Laufzeit in Maschinencode übersetzt (Just-in-time-Compiler). Auch Python übersetzt ein Programm zuerst in Bytecode (.pyc), der dann vom Python-Interpreter ausgeführt wird. Viele Fehler, die ein Java-Compiler vor dem Start meldet, bemerkt Python deshalb erst zur Laufzeit.

2. Die Phasen eines Compilers

Der Übersetzungsprozess eines Compilers lässt sich in mehrere Phasen unterteilen. Hier sind die Hauptphasen:

  1. Lexikalische Analyse (Scanner, Lexer)
  2. Syntaktische Analyse (Parser)
  3. Semantische Analyse
  4. Zwischencode-Erzeugung
  5. Optimierung
  6. Code-Erzeugung

3. Lexikalische Analyse – endliche Automaten in Aktion

Bei der lexikalischen Analyse wird der Quellcode in Tokens zerlegt. Ein Token ist die kleinste sinnvolle Einheit in einer Programmiersprache, wie zum Beispiel Schlüsselwörter, Bezeichner, Literale oder Operatoren.

Beispiel 1 einfach

Ausgangssituation: Die Zeile summe = summe + 42; wird zerlegt in

BEZEICHNER(summe) ZUWEISUNG BEZEICHNER(summe) PLUS ZAHL(42) SEMIKOLON

Der Automat für ZAHL hat einen Startzustand und einen akzeptierenden Zustand „Zahl“ mit einer Schleife für die Ziffern 0–9. Der Automat für BEZEICHNER akzeptiert [a-zA-Z_][a-zA-Z0-9_]*.

  1. Erstes Zeichen entscheidet: s ist ein Buchstabe, also startet der BEZEICHNER-Automat. Warum? Nur dieser Automat hat für einen Buchstaben einen Übergang aus dem Startzustand.
  2. So weit wie möglich lesen: u, m, m, e bleiben in der Schleife des Endzustands; beim Leerzeichen gibt es keinen Übergang. Token: BEZEICHNER(summe). Warum? Lexer suchen das längste passende Teilwort – sonst würde aus summe eine Folge von fünf Ein-Buchstaben-Bezeichnern.
  3. Leerzeichen überspringen: Es erzeugt kein Token, es trennt nur.
  4. Einzelzeichen-Token: = → ZUWEISUNG, später + → PLUS und ; → SEMIKOLON.
  5. Zahl lesen: 4 startet den ZAHL-Automaten, 2 bleibt in der Schleife, bei ; endet das Token ZAHL(42).

Ergebnis: sechs Tokens, wie oben angegeben.

Kontrolle – die Grenze des Lexers: 2summe ergibt ZAHL(2) BEZEICHNER(summe). Der Lexer meldet keinen Fehler; dass eine Zahl nicht direkt vor einem Bezeichner stehen darf, erkennt erst der Parser.

4. Syntaktische Analyse – Kellerautomaten und Grammatiken

Der Parser überprüft, ob die Abfolge der Tokens den Regeln der Programmiersprache entspricht. Er erstellt dabei oft einen Syntaxbaum, der die Struktur des Programms repräsentiert.

Hinweis: Parser als Kellerautomat

Die Syntax der meisten Programmiersprachen lässt sich durch kontextfreie Grammatiken beschreiben. Der Parser, der die syntaktische Analyse durchführt, arbeitet wie ein Kellerautomat, der diese Grammatik verarbeitet.

5. Semantische Analyse – über Grammatiken hinaus

Bei der semantischen Analyse wird die Bedeutung der Anweisungen geprüft. Das geht über die Möglichkeiten kontextfreier Grammatiken hinaus: Ob eine Variable vorher deklariert wurde, hängt vom „Kontext“ an einer ganz anderen Stelle im Programm ab. Der Compiler verwendet dafür eine Symboltabelle.

Beispiel 2 komplex

Ausgangssituation: if (a > 0) b = a * 2; in Java

  • Lexer: IF KLAMMER_AUF BEZEICHNER(a) GRÖSSER ZAHL(0) KLAMMER_ZU BEZEICHNER(b) ZUWEISUNG BEZEICHNER(a) MAL ZAHL(2) SEMIKOLON
  • Parser: erkennt nach der Grammatik <if> ::= "if" "(" <ausdruck> ")" <anweisung> eine if-Anweisung und baut den Syntaxbaum; a * 2 hängt wegen „Punkt vor Strich“ als eigener Teilbaum unter der Zuweisung.
  • Semantik: Sind a und b deklariert? Ist a > 0 vom Typ boolean? Passt der Typ von a * 2 zum Typ von b?

Die drei Phasen nacheinander:

  1. Lexer: if passt zwar auch auf den Bezeichner-Automaten, steht aber in der Liste der Schlüsselwörter und wird deshalb zum Token IF. Warum? Sonst könnte der Parser eine if-Anweisung nicht von einer Variablen namens if unterscheiden.
  2. Parser: Er arbeitet nur noch mit den Token-Typen, nicht mit den Namen. Er prüft die Reihenfolge IF, KLAMMER_AUF, Ausdruck, KLAMMER_ZU, Anweisung – wie ein Kellerautomat, der sich die offene Klammer merkt.
  3. Semantische Analyse: Sie schlägt a und b in der Symboltabelle nach (Deklaration und Typ) und prüft die Typen. Warum erst hier? Ob b vorher als int deklariert wurde, steht an einer ganz anderen Stelle im Programm – das kann keine kontextfreie Grammatik prüfen.

Ergebnis: Fehlt die schließende Klammer, meldet der Parser einen Fehler; ist b als String deklariert, meldet die semantische Analyse „incompatible types“ – zwei verschiedene Phasen, zwei verschiedene Fehlermeldungen.

6. Verbindung zu Automaten und Grammatiken

Compiler-Phase verwendete Theorie Modell Beispiel
Lexikalische Analyse reguläre Ausdrücke (Typ 3) endlicher Automat Erkennung von if, while, Bezeichnern, Zahlen
Syntaktische Analyse kontextfreie Grammatiken (Typ 2) Kellerautomat Überprüfung von Klammerstrukturen und Anweisungsaufbau
Semantische Analyse kontextabhängige Regeln (Symboltabelle, Typsystem) allgemeine Algorithmen Typprüfung, Variablendeklaration, Parameteranzahl

Ein Mini-Scanner in Python

Ein Scanner lässt sich ohne Bibliothek programmieren: Eine Funktion ordnet jedem Zeichen eine Zeichenklasse zu, eine Schleife liest den Text und wählt nach dem ersten Zeichen den passenden „Automaten“. Die inneren Schleifen sind genau die Schleifen an den Endzuständen „Zahl“ und „Bezeichner“.

Beispiel 3 Programmierung

Ausgangssituation: Einfache Ausdrücke mit Zahlen, Bezeichnern, den Rechenzeichen + - * /, Zuweisung, Klammern und Semikolon sollen in Tokens zerlegt werden. Jedes Token ist ein Tupel (Typ, Text).

OPERATOREN = {
    "+": "PLUS", "-": "MINUS", "*": "MAL", "/": "GETEILT",
    "=": "ZUWEISUNG", "(": "KLAMMER_AUF", ")": "KLAMMER_ZU",
    ";": "SEMIKOLON",
}


def zeichenklasse(z):
    if z in "0123456789":
        return "ziffer"
    if z.isalpha() or z == "_":
        return "buchstabe"
    if z == " ":
        return "leer"
    if z in OPERATOREN:
        return "operator"
    return "unbekannt"


def scanne(text):
    tokens = []
    i = 0
    while i < len(text):
        klasse = zeichenklasse(text[i])
        if klasse == "leer":
            i = i + 1                      # Leerzeichen trennen nur
        elif klasse == "operator":
            tokens.append((OPERATOREN[text[i]], text[i]))
            i = i + 1
        elif klasse == "ziffer":           # Automat für ZAHL
            start = i
            while i < len(text) and zeichenklasse(text[i]) == "ziffer":
                i = i + 1
            tokens.append(("ZAHL", text[start:i]))
        elif klasse == "buchstabe":        # Automat für BEZEICHNER
            start = i
            while i < len(text) and zeichenklasse(text[i]) in ("buchstabe", "ziffer"):
                i = i + 1
            tokens.append(("BEZEICHNER", text[start:i]))
        else:                              # kein Automat passt
            tokens.append(("FEHLER", text[i]))
            i = i + 1
    return tokens


# Testfälle: (Eingabe, erwartete Tokenliste)
tests = [
    ("summe = summe + 42;",
     [("BEZEICHNER", "summe"), ("ZUWEISUNG", "="), ("BEZEICHNER", "summe"),
      ("PLUS", "+"), ("ZAHL", "42"), ("SEMIKOLON", ";")]),
    ("x1*(y+7)",
     [("BEZEICHNER", "x1"), ("MAL", "*"), ("KLAMMER_AUF", "("),
      ("BEZEICHNER", "y"), ("PLUS", "+"), ("ZAHL", "7"), ("KLAMMER_ZU", ")")]),
    ("3a", [("ZAHL", "3"), ("BEZEICHNER", "a")]),
    ("a # b", [("BEZEICHNER", "a"), ("FEHLER", "#"), ("BEZEICHNER", "b")]),
    ("", []),
]
for eingabe, erwartet in tests:
    ergebnis = scanne(eingabe)
    print(repr(eingabe), "ok" if ergebnis == erwartet else "FEHLER")

print(scanne("x1*(y+7)"))
  1. Zeichenklassen: zeichenklasse entspricht den Spalten einer Übergangstabelle: Alle Ziffern verhalten sich gleich, alle Buchstaben auch. Warum? So braucht der Scanner keine Tabelle mit hunderten Spalten.
  2. Ablauf für "x1*(y+7)": i = 0, x ist ein Buchstabe → innere Schleife liest x und 1 (Ziffern sind im Bezeichner erlaubt), stoppt bei * mit i = 2 → BEZEICHNER(x1). Dann * → MAL, ( → KLAMMER_AUF, y → BEZEICHNER(y), + → PLUS, 7 → ZAHL(7), ) → KLAMMER_ZU.
  3. Längstes Teilwort: Die inneren while-Schleifen laufen, solange der Automat im Endzustand bleiben kann. Die Bedingung i < len(text) verhindert, dass am Textende über die letzte Stelle hinaus gelesen wird.
  4. Fehlerfall: Für # gibt es keinen Automaten. Der Scanner erzeugt ein Token FEHLER und liest weiter, damit er weitere Fehler in derselben Zeile melden kann.

Ergebnis (Ausgabe des Programms):

'summe = summe + 42;' ok
'x1*(y+7)' ok
'3a' ok
'a # b' ok
'' ok
[('BEZEICHNER', 'x1'), ('MAL', '*'), ('KLAMMER_AUF', '('), ('BEZEICHNER', 'y'), ('PLUS', '+'), ('ZAHL', '7'), ('KLAMMER_ZU', ')')]

Kontrolle: Der Testfall "3a" zeigt die Grenze aus Beispiel 1: Der Scanner liefert ohne Fehlermeldung ZAHL und BEZEICHNER. Die leere Eingabe ergibt eine leere Tokenliste.

Praxisbezug: Compilerbau im Berufsleben

Alltag: Jede App auf deinem Smartphone wurde von einem Compiler übersetzt. Die Fehlermeldung „missing semicolon“ in deiner Entwicklungsumgebung stammt direkt aus Lexer oder Parser. Auch Webbrowser enthalten Compiler: JavaScript wird beim Laden einer Seite geparst und in Maschinencode übersetzt.

Beruf: Compilerentwicklerinnen und -entwickler arbeiten bei Chip- und Softwareherstellern an Werkzeugketten, z. B. für Mikrocontroller in Autos und Industrieanlagen – ein Bereich, der im „Silicon Saxony“ rund um Dresden stark vertreten ist. Mit Lexer- und Parser-Generatoren (ANTLR, flex/bison) entwickeln Softwarefirmen außerdem eigene domänenspezifische Sprachen, etwa für Konfigurationen, Datenbankabfragen oder Testskripte.

Das Wichtigste

Compiler: Übersetzt den gesamten Code vor der Ausführung und kann dabei viele Fehler schon vor dem Programmstart melden.

Interpreter: Übersetzt und führt den Code Anweisung für Anweisung während der Ausführung aus.

Phasen der Analyse: lexikalisch → syntaktisch → semantisch. Die ersten beiden beruhen auf formalen Sprachen, also auf Automaten und Grammatiken.

Lexikalische Analyse: Jeder Token-Typ wird durch einen regulären Ausdruck beschrieben, daraus entsteht ein endlicher Automat. Seine akzeptierenden Zustände entsprechen den Token-Typen, z. B. „Zahl erkannt“.

Semantische Analyse: Prüft unter anderem die Typkorrektheit, ob Variablen vor ihrer Verwendung deklariert sind und ob Funktionen mit der richtigen Anzahl von Parametern aufgerufen werden.
